## Decisions resolved live

1. **Target sizes — parity, not independent doubling.** Session 40 had
   already grown Encryption/Root to 21 each (six new win-condition
   mechanisms) while Exploit/Malware sat at their original 15. Doubling
   each independently would have widened that asymmetry (30/30/42/42);
   parity converges all four on ~30 (14c/10u/6r), so Exploit/Malware get
   +15 each and Encryption/Root only +9. User confirmed parity and added
   scope I hadn't proposed: Neutral also roughly doubles (9→18, "another
   9-ish"), and the 18 class-starting-loadout pieces get a quality
   review, not just the 4 archetype pools + Neutral.
2. **Reuse-first for Exploit/Malware's payload thinness.** Exploit has 4
   payload kinds, Malware 2 (vs. Encryption's 7, Root's 6) — a real
   asymmetry. Confirmed: fill real coverage gaps with existing payload/
   trigger/tag combinations first, invent new mechanisms only if drafting
   actually hits a wall. User added the operating rule that made the
   rest of the session possible: overlap in *individual* trigger or
   payload usage across pieces is fine, a subroutine only needs a
   *unique combination* to earn its slot.
3. **Session scope: audit + plan only, no authoring.** Given the real
   scale (57 pieces across 5 pools, bigger than any prior content pass —
   Mods was 17, Burners/Events was 8+8, session 40's own sample was 12)
   and the user's own prior framing that this is explicitly multi-
   session, confirmed this session stops at a written plan; a future
   `/dev-session` authors the real data.
4. **`ChainedTrigger` redesign — the session's real pivot.** Auditing
   for real coverage gaps surfaced 3 pool pieces (Drive-By Exploit,
   Chain Infection, a Root uncommon) permanently dead for 5 of 6 classes
   — each chains off a class-exclusive starting-loadout id no other
   class's reward pool can ever grant. I proposed keeping id-based
   chaining as one of three match modes (id/archetype/tag) and
   redesigning just those 3. The user pushed further: drop id-based
   matching from pool content *entirely*, since nothing in the
   acquisition system (shop slate, combat rewards) guarantees a player
   draws both halves of any specific pair in one run — even the 4
   existing pool-to-pool chains carry real run-to-run dead-content risk,
   just less severe than the 3 permanently-broken ones. `afterSubroutineId`
   stays in the type, reserved for contexts that *do* guarantee
   co-presence (a fixed starting loadout, or a future Event that grants
   a matched pair at once) — matches the user's own stated carve-out.
   All 7 existing chains convert to `afterArchetype`/`afterTag` matching.
5. **His Heels needs a real constraint.** The user flagged, correctly,
   that His Heels (the cut card being a Jack) is outside either player's
   control and asked how often it actually fires. Checked with
   `scripts/occurrence-frequency.ts` rather than guessing: 0.076/hand,
   the rarest occurrence category in the game — a Threshold-variation
   piece using it would be functionally dead content (expected ~0.2
   occurrences per side in a real fight), the same "content that can't
   become ready" bug class as Kernel Panic/Quarantine Ward. Resolved:
   Instant-variation only, rare-tier only, exactly one piece across the
   whole 57-piece pass (Doomsday Clock).
6. **A 6th tag, Direct, added.** Counted real tag coverage: 38 of 99
   existing pieces (38%) carried no tag, and my own first-pass draft of
   the 57 new pieces was worse (63% untagged). The 5 existing tags all
   describe a specific mechanism (delay, bypass, defense, chaining,
   persistence) — there was no tag for "immediate, single-shot, none of
   the above," which is the single most common shape in the pool. Added
   Direct rather than stretch an existing tag to cover it (would have
   diluted what that tag means). User confirmed in one round.
