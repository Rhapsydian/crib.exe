## Goal

Audit and roughly double the general Mod pool (23 Mods at the time: 6
class-exclusive starting passives + 17 validated general-pool Mods from
session 32's content table), mirroring the audit-and-expand treatment the
player and enemy pools already got.

## Decisions resolved live

1. **Session scope: design-only, or design-and-implement same session?**
   Deliberately left open rather than assumed either way going in (unlike
   session 43's same-session call for the smaller enemy pass) — resolved
   as design first, decide on implementation once the actual content plan
   existed.
2. **Curses/negative-effect Mods — punted a fourth time, but for a real
   reason this time.** Three prior sessions (30, 31, 32) had punted this
   without ever attaching a reason. Resolved: curses need their own
   acquisition-channel decision first (a specific "guaranteed-bad" slot,
   mirroring StS's Necronomicon/Cursed Key/Sozu), which isn't this
   session's job — bundled with whatever future session finally designs
   Event nodes, since an event choice is the most natural home for a
   curse. The Events-as-Mod-reward-channel gap (named as "a probable
   third channel" back at session 30, never followed through) was
   confirmed still true by checking `events.ts`/`event-types.ts` directly,
   and parked alongside it rather than folded into this content pass.
3. **Whether new content should reach for session 40's 6 new engine
   mechanisms (3 Encryption payloads, 3 Root mechanisms)**: confirmed
   opportunistically, not as a target — don't manufacture a Mod just to
   exercise a new mechanism, but don't avoid one either if the audit finds
   a natural fit. (One rare, Session Hijack Relay, ended up using the new
   `sessionHijack` payload this way.)
4. **A real migration inconsistency found and fixed, not part of new
   content**: `createCombatState` folds each class's starting-passive Mod
   into `ownedModIds` specifically so `hasMod` dispatch works for all 6
   class-exclusive Mods (session 30's stated migration). Four of six
   (Sleeper Cell, Zero Day, Feedback Loop, Return to Sender) actually use
   `hasMod`; Foothold and Primed never were migrated, still gating on
   `combatState.classId` directly. Behaviorally inert today (class↔Mod
   ownership is 1:1 by construction) but real inconsistency — confirmed
   fixable with zero behavior change (every call site already goes
   through the fold), then fixed.
5. **Implement now, once the design draft landed.**

## Work completed

**Design**: full 17-piece content plan doubling every rarity tier (7/6/4
→ 14/12/8), closing two real hook-coverage gaps found by re-reading the
hook dispatch code rather than assumed from prior docs — plain `onTick`
had zero Mod content ever, and `onEncounterResolved`'s "Heat mitigation"
use case (one of three named back at session 31) was never exercised.
Authored the 3 Malware Amplifier archetype siblings (Exploit/Encryption/
Root) the session-32 table flagged as implied but undrafted. Verified
Tagged Firmware's tag choice (`daemon`) is still the most-represented tag
post-session-41's retag, rather than assuming it still held.

**Implementation**: all 17 pieces authored in `mods.ts`/`mod-types.ts`.
Combat-scoped hooks wired in `resolve.ts` (Cold Boot/onCombatStart,
First Contact/onGaugeCross50, the 3 Amplifiers/onFire, Surge
Protector/onIncomingDirectBurst, Redline/onTick). Run-scoped hooks in
`mods.ts`/`run.ts`/`encounters.ts` (Quiet Hours/onMove needed a new
`applyQuietHoursMod` since it touches playerState, not just a flat Heat
transform; Petty Theft/Heat Sink extend `applyOnWinEncounterResolvedMods`;
Fast Learner extends the Salvage Protocol pattern via a new shared
`applyFirstArchetypeUpgradeMod` helper; Init Script extends
`applyOnModAcquiredMods`). `triggers.ts`'s `updateSubroutineState` gained
a second, independent reduction parameter for Threshold Exploit
(Occurrence-Threshold's integer `bankTarget` needed a flat-fraction
reduction, not a reuse of Accumulator's multiply-a-raw-magnitude shape —
threaded through `combat.ts`'s `applyOccurrenceToState`). `shop.ts`'s
three offering functions gained a parallel `extraUncommons` parameter
alongside the existing `extraCommons`, for Scrap Merchant.

**A real design correction made during implementation, not assumed safe
from the draft alone**: Surge Protector's draft called for conditioning
its bigger mitigation on the player's own Heat sitting below half of max
— but `CombatState` has no Heat field at all (Heat is a between-fights
resource tracked in `RunPlayerState`, never threaded into combat), so a
Heat-conditional check would have meant a real architecture change just
for one Mod. Redesigned to a per-fight one-shot instead (first incoming
direct burst each fight, not every one) — conditional on timing rather
than a resource, zero new engine surface.

**Two real naming collisions caught and fixed before finalizing**: the
draft names "Idle Process" and "Failover" both already existed as real
subroutines elsewhere in the pool (Ghost's starting-loadout piece; a
Neutral common), found by grepping every new id/name against
`subroutines.ts`/`enemy-subroutines.ts`/`enemies.ts`/`burners.ts`/
`events.ts` rather than assuming a fresh design-session name was actually
fresh. Renamed to **Init Script** and **Heat Sink** throughout code,
tests, and docs. One incidental bug caught and fixed during the rename: a
sed pass turned an object-literal key `failover:` into the invalid bare
identifier `heat-sink:` (hyphens aren't legal in an unquoted key) —
caught immediately by `npm run check`, fixed by quoting it.
