A long, continuous session spanning a real day rollover: independent

balance pass (layer 4 complete, layer 2's root cause found), a full

## Part 1 — Independent per-side gauge/win thresholds

### Goal

Continuing from session 39's gatekeeper-ablation audit, which flagged
layer 4 (Null Session too hard, Kernel Panic too easy) as the widest
spread in the roster. Before tuning anything, the user wanted the
architecture gap session 25/39 had already flagged fixed first:
`CombatOptions.gaugeThreshold`/`winThreshold` were each a single number
applied to *both* sides of a fight, even though the underlying
`DuelGauge`/`InitiativeGauge` structs already modeled a side's own
threshold independently.

### Key decisions

Resolved live via `/decision-session`:

- **Plumbing only this session** — independent per-side storage plus an
  optional per-gatekeeper override, zero numeric/balance change. The
  actual balance pass was deliberately sequenced after, not part of it.
- **Also build a dynamic Mod-hook mechanism**, not just a static field —
  the user wanted this to "expand the content design space," not just
  serve as a tuning knob. Reused the existing `onCombatStart` hook
  (already real, Warm Boot uses it) rather than inventing a new one.
- Regular/elite enemies stay on the flat global constants for both
  thresholds (no per-layer formula the way `magnitudeScaler` gets one) —
  a real, separate future question, out of scope for a zero-behavior-
  change session.

### Work completed

Checkpoints A-F, implemented same-session (`0768db2`): `CombatOptions`/
`createCombatState` widened to `[player, enemy]` tuples; `EnemyDefinition`
gained optional `gaugeThreshold?`/`winThreshold?` (gatekeeper-only,
mirroring `magnitudeScaler`); new `gaugeThresholdFor`/`winThresholdFor`
accessors wired into `encounters.ts` and `scripts/gatekeeper-check.ts`;
new `adjustSideWinThreshold` primitive in `resolve.ts` (the mechanism a
future Mod could call, proven with a direct unit test, no real Mod
shipped); ~150 existing call sites across 7 test files and
`scripts/sweep.ts` migrated from bare scalars to tuples — a much bigger
mechanical surface than the spec itself anticipated (several files call
`createCombatState` directly with positional args, not the object-
literal `gaugeThreshold:`/`winThreshold:` shape the original grep
targeted). 572/572 tests passing (from 564), a 50-seed regression sweep
came back byte-identical before/after, confirming true zero behavior
change with every override left unset.

### Deferred / parked

- No gatekeeper actually got a real override value this checkpoint —
  that was always the next pass's job.
- The dynamic hook is proven but unused — no real Mod calls
  `adjustSideWinThreshold` yet.

## Part 2 — Gatekeeper balance pass (layer 4 complete, layer 2 root cause found)

### Goal

Use the new levers to work through session 39's audit findings,
layer by layer, per its own suggested order (widest spread first).

### Key decisions

- **Null Session**: diagnosed to `null-session-passive` — a flat,
  unconditional +7 credit the instant the player crosses 50% of *their
  own* threshold, no counterplay. Fixed via `winThreshold: 65` (up from
  50), tested against 65 and 80 — 65 already captured nearly all the
  gain, 80 plateaued. Locked in 65.
- **Kernel Panic**: instrumented real fire frequency directly (a
  deleted scratch script, this project's own convention) — real fights
  average 2.33 hands, both its credit-capable pieces (Total Pwnage,
  Epidemic) fire in ~10% and ~0.6% of fights respectively. Neither
  `winThreshold` nor `gaugeThreshold` moved the number at all when
  tested — a subroutine that never becomes ready doesn't fire more
  often just because it's the enemy's turn more often. Fixed with three
  bespoke enemy-only replacement pieces (Stack Overflow, Memory
  Corruption, Failsafe Reboot — same payload flavor, `occurrence:
  threshold`->`instant` / `accumulator`->`always` trigger-shape rework),
  mirroring session 39's `enemy-subroutines.ts` precedent. Magnitude
  tuned across three candidates (checked against both isolated and
  full-run numbers — the isolated read alone was misleading), locked in
  the smallest that still cleared the "no longer 100%" bar. Operator's
  own win rate against Kernel Panic was identical across all three
  candidates — flagged as a distinct, magnitude-insensitive finding,
  not chased.
- **User pushback, correctly**: an earlier "the 9-15% band is stale"
  framing (comparing skill=0.85 numbers against a band calibrated at a
  different default) was wrong — verified at skill=0.5, the band is
  still a reasonable reference point. Noted for future checks.
- **Layer 2 diagnosed, not fixed**: Incident Response (hard,
  well-populated kit, all three pieces fire at healthy rates — *not*
  dead content like the layer-4 pair), The Quarantine Ward (easy, the
  identical dead-content problem as Kernel Panic, shares the exact same
  `epidemic`/`cold-storage` pieces), Zero-Sum (easy, a partial version —
  `dead-drop` never fires, `total-pwnage` underpowered). The Incident
  Response finding redirected the whole session — see Part 3.
- **`gaugeFillAbove` fixed** (`9c6d870`, user's explicit direction:
  "fix the bug first"): confirmed session 39's own banked-but-
  unconfirmed suspicion — the condition reads the cyclical
  InitiativeGauge, not real win-progress, so Vulnerability Scan (a
  piece authored as a rare late-game punish) fired 1.48 times in a
  2.46-hand fight. Migrated Vulnerability Scan/Honeypot to
  `breachContainmentAbove` (already used by `enemy-subroutines.ts` for
  the identical reason); Honeypot was also missing `reactive: true`
  entirely, a second, compounding bug. Priority Override/Sinkhole
  (Root) also use the condition but were deliberately left alone —
  their own design intent (frequent priming, tempo catch-up) is
  genuinely compatible with the real cyclical behavior.

### Work completed

Commits `98b1adc` (Null Session), `897851e` (Kernel Panic),

### Deferred / parked

## Part 3 — Archetype Win-Condition Audit

### Goal

The user's own pivot, after `gaugeFillAbove`: "do we need to take a
hard look at the combat system and archetypes?" Assessed directly —
every finding so far traced to *content* (dead triggers, one buggy
shared condition), not the combat system's own mechanics. The user
redirected one level deeper anyway: audit the archetypes themselves,
since "each archetype needs win conditions" — both a real path to win
as a player, and a real path to contain as an enemy.

### Key decisions

- Confirmed directly from `resolve.ts`'s payload dispatch (not assumed
  from docs): **Encryption and Root had zero payload kinds that credit
  the caster's own gauge.** "Mitigation can't win alone" was a
  deliberate, stated property; this was a separate, unintended gap.
- A broader empirical audit (all 12 gatekeepers, 3,151 real fights) found
  the hand-20 attrition backstop is reached almost never in practice —
  only Firewall Prime (17.1%, pure Encryption, structurally had no other
  path) and Null Session (3.6%) ever resolve that way; the other 10
  gatekeepers sit at a flat 0.0%. Not acted on this session.
- **Encryption fix**: reuse Ghost's own proven Return to Sender passive
  mechanism (already tuned across two balance passes) rather than invent
  something new. Three new payload kinds — `wardCounter` (arms an
  ongoing absorb-credits-back effect via `passiveState`, since
  `wardShield` is pooled, not per-casting-subroutine), `drainingHot`
  (each tick credits the caster on top of the usual suppression), and
  `wardBash` (the user's own idea: spend a fraction of *current*
  wardShield for an instant credit — a high fraction naturally consumes
  the whole shield, no separate "consume everything" flag needed).
- **Root fix, three options weighed live**: extending
  `instantManipulation` with an `ownWinGauge` target (rejected — the
  user's own read: "that's just directBurst"); **Session Hijack**
  (chosen — a genuine two-sided win-gauge transfer, capped at what the
  opponent actually had banked, composes for free from
  `reduceWinGauge`+`creditWinGauge`); a recon-payoff idea ("Data
  Ransom," floated, not built — its simple form was too close to
  directBurst-with-a-trigger, its rich form needed real new plumbing).
- **A real, separate engine bug found via user correction**: the user
  caught that the pegging AI was supposed to be informed by Root's own
  Directory Traversal piece. Verified directly — `scorePegCandidate`'s
  own type signature explicitly excluded `knownOpponentHand`
  (`Pick<PlayContext, 'legalCards' | 'count' | 'sequence'>`), even
  though the data had flowed correctly end-to-end since session 24.
  Fixed: `RISKY_COUNTS`' blanket guess now only runs when the opponent's
  hand isn't actually known; when it is, defensiveRisk resolves two real
  threats (a 15/31-completing card, a same-rank pairing card) instead.

## Part 4 — Root trigger mechanisms

### Goal

The user liked Root getting bespoke *trigger* effects better than
bespoke payloads ("more on theme for the archetype") and proposed two
concrete ideas mid-conversation: a "trap" that gains Breach progress
when the enemy scores a crib hand > 4, and a strong reactive effect for
rare scoring events like a pair royal, watching either side.

### Key decisions

- Clarified which of two readings the user meant (a composition of
  existing mechanisms vs. a genuinely new one bypassing the normal
  pipeline) before building anything — the user confirmed the latter
  ("Reading 2").
- Both ideas were judged genuinely novel and complementary (one watches
  a single event, one watches an aggregate hand outcome) rather than
  variations of the same thing, and built together at the user's
  request ("Lets build both").

### Work completed (`d4293c6`)

Two new trigger families, both bypassing the normal ready-flag/turn-gate
pipeline entirely (`isReady` returns `false` for both unconditionally):
**`rareOccurrence`** (watches a specific Occurrence category at or above
a magnitude floor, from *either* side — the one deliberate break from
Occurrence's own self-scoping rule; checked inside `combat.ts`'s
existing per-occurrence loop) and **`handOutcome`** ("Crib Trap" — watches
one phase's own aggregate total for a just-resolved hand, read directly
off `HandResult`'s already-computed scores; checked once per hand right
after it resolves). Both pair with existing credit payloads rather than
needing new ones. 610/610 tests (16 new).

**A real accuracy bug caught and fixed before it compounded** (`60f1bcc`):
the doc comments and test fixtures for `rareOccurrence` claimed a Pair
occurrence's magnitude runs 2/3/4 for pair/pair-royal/double-pair-royal.
Verified directly against `scoring.ts`'s `pairEvents` and `pegging.ts`'s
own breakdown — the real values are 2/6/12 (raw points, `n*(n-1)`), not
a count-of-a-kind. The engine logic itself was never wrong (the
comparison is generic); this was purely inaccurate documentation,
caught while scoping the next part's content sample.
