## Key decisions

Opened by reading the actual pipeline before proposing anything:
`resolve.ts`'s 5 existing enemy-passive hook points (all combat-internal,
since enemies don't persist past one fight) versus a complete absence of
any hook mechanism in `run.ts`/`encounters.ts`/`shop.ts` — but those
files already pass around two rich structs (`EncounterOutcome`,
`RunEvent`) that turned out to cover most of what a run-level Mod would
need to observe, without inventing new state.

Resolved live, one decision at a time:

1. **Coarse hooks with rich context, not fine-grained ones per
   concern** — a Mod reads whichever field it needs off a shared
   struct, the same "dispatch mechanism, not a declarative DSL"
   philosophy session 27 already established for the enemy registry.
2. **All hooks chainable/mutation-capable**, not read-only — the same
   fold/thread pattern the enemy-passive dispatch already uses
   (`applyEnemyOnFirePassives(combatState, ...) -> combatState`,
   chained). Surfaced when the user asked whether a combat-end hook was
   needed for reward-altering Mods; the real answer was that
   `onEncounterResolved` had been framed too narrowly (read-only)
   rather than that a new hook was missing.
3. **No dedicated combat-end hook** — `onEncounterResolved` (run-scoped)
   already covers "how did the fight go," since reward computation
   (`resolveEncounter`) doesn't depend on combat-internal state anyway.
4. **`onSubroutineAcquired` included**, distinct from
   `onEncounterResolved` — the latter only ever sees the *offered*
   `rewardOptions`; the real pick happens later in `playRun()` via
   `AcquisitionStrategy`. The user's own motivating example: "when you
   acquire a Malware subroutine, upgrade it once."
5. **`onFire` widened** from `archetype`-only to the full firing
   `SubroutineDefinition` (id + tags + archetype) — caught while
   stress-testing the catalog against tag-affinity Mods (one of the two
   hook categories session 30 named as core): archetype alone can't
   support a Mod like "your Trap-tagged subroutines hit harder."
6. **`onShopSlateGenerated` added** for Shop-discount Mods — prices are
   fixed before `EncounterOutcome.shopPurchase` exists, so a
   price-altering Mod needs an earlier hook than the post-purchase one.
7. **`onModAcquired` added**, raised mid-session by a concrete Mod idea
   the user had: grant an always-slotted subroutine — installed
   permanently, reorderable like any other loadout piece (participates
   in normal top-to-bottom chaining), but exempt from the slot cap and
   locked against removal. Doesn't fit either of session 30's two engine
   buckets (must live *inside* `installedLoadout`'s ordering, unlike a
   reactive-subroutine Mod which fires outside it). Resolved as a
   one-time structural-mutation hook (fires once at acquisition, against
   `RunPlayerState`) plus a new per-entry loadout marker
   (`grantedByModId?: string`) that the slot-cap check and uninstall
   action special-case — reorder and fire-on-turn/chaining logic need no
   changes. Upgrading the granted piece falls out for free via the
   existing Merge/rank mechanism.

## Notable problem-solving notes

- Reading `resolveEncounter`'s actual body before proposing a hook
  design paid off directly: it revealed reward computation never
  touches combat-internal state (quality keys off encounter tier alone),
  which is what let "no dedicated combat-end hook" be a confident
  recommendation rather than a guess.
- The reward-altering-Mods question (decision 2) is a good example of a
  user question that looked like "do we need a new hook" but turned out
  to be "the hook I already proposed was underspecified" — worth
  re-examining an existing proposal's *shape* before reaching for a new
  hook point when a gap gets flagged.
