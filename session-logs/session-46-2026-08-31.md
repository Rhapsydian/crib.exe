## Decisions resolved live

1. **Neutral fills a credit-gap** (rung 1), not just rung 2. Chosen over
   a whole-loadout "credits nowhere" check after measuring: all 6 classes
   start with at least one credit-capable piece, so that check would have
   been unreachable dead code, while 4 of 6 start missing one in a
   specialization (Saboteur/Operator: root; Warden: encryption; Ghost:
   both). My initial recommendation was wrong and the user's lean was
   right — the stated downside (neutral outranking on-archetype) doesn't
   exist, since both reach rung 1 and rung 2 breaks the tie.
2. **Reorder covers all three `ChainedTrigger` match modes**, not just
   `afterSubroutineId` as spec'd — measured that *zero* pieces use that
   variant (session 42 converted every chain to archetype/tag), so the
   spec's rule was dead code; widening it covers 14 real pieces.
3. **Neutral pool enters at full weight, everywhere, with no rarity
   reweighting** — see the fix section below.

## Deviations from the spec, and why

- **Checkpoint E (Merge)**: the spec said reuse checkpoint B's ladder,
  but `fillsCreditGap` *inverts* on a Merge candidate — an installed
  credit-capable piece scores as filling no gap (it already fills it),
  while a benched one scores as filling one, so the ladder would rank
  benched above installed. Re-rung on what a Merge actually turns on:
  installed → credit-capable → archetype → banked material.
- **Checkpoint F (reorder) call site**: applied once per node after the
  whole resolution block rather than at the four places that mutate
  `installedLoadout`. The rule is pure and idempotent (test pins this),
  so it's equivalent and can't miss a future acquisition route.
- **Checkpoint G (swap-out)**: same inversion as E, fixed by ranking
  every piece *counterfactually* against the loadout without it, so a
  sole credit provider is protected from eviction with no special case.
- **Checkpoint I**: `EventChoiceStrategy` never received Heat, so
  `gambleSafetyMargin` had nothing to check. Widened the signature —
  `resolveEncounter` already had `currentHeat` in hand.

## The bug the smoke sweep caught

First full-profile sweep came out **worse than the dumb baseline**:
10/240 wins vs floor's 26/240, `noRoute` doubling. A single-strategy
ablation isolated it to swap-out. Mechanism: `rarityOf()` reports
`'common'` for all 18 class starting-loadout pieces — not because they're
weak but because they carry *no authored rarity at all* — so the rarity
rung parked every hand-designed starting piece at the bottom of the
eviction order. Measured: **73% of authored starting kits dismantled**.

Fixed by dropping rarity from the swap comparison, the same reasoning
checkpoint E had already applied to Merge: rarity describes how a piece
is *distributed*, not how good it is in a loadout, and is only meaningful
for pieces actually authored into a tier. Result: **42/240 vs floor's
26/240**. Regression-guarded by a unit test and an end-to-end
starting-loadout-preservation test.

Sample-size caveat recorded at the time: at 240 runs the standard error
is ~±6 wins, so floor 26 → synergy 42 is real signal (~2.7 SE) but the
per-ablation gaps (42 vs 47 vs 49) are all noise. Swap-out is the one
component with no positive evidence even after the fix.

## Neutral pool fix

Found while measuring how often the ladder's archetype rung actually
fires: **neutral was 0.0% of offers for 5 of 6 classes**. All 18
`NEUTRAL_POOL` pieces were unreachable through every acquisition path
since session 28 — combat rewards, Shop slate and Event grants all derive
from `rewardPoolForClass`, which never included them. Only entry point in
the whole game was one scripted Event grant. User confirmed unintended.

Three questions resolved before implementing: **full weight** (no new
machinery needed; a reduced weight would be a number with no calibration
target), **everywhere** (not a real fork — one function feeds all three
routes), **no rarity reweighting** (measured: neutral's 8/6/4 split is
near-proportional to the class pools' 28/20/12, so a standard-tier rare
draw moves 2.1% → 2.2%).

## Found, diagnosed, not fixed — the Heat trigger bug

The neutral change made a full sweep hang (4GB OOM). Diagnosed in depth;
**pre-existing, not caused by the change** — the hanging loadout contains
no neutral pieces and reproduces with zero Mods; the pool change only
altered which pieces a seed drew.

Ruled out along the way: the pegging loop (instrumented, never exceeded
500 iterations), the map loop (<2000 iterations), the hand loop (bounded
at `HARD_RESOLUTION_HAND` 20), all 13 Mods, and both Burners. Isolated by
bisection to a single piece, **`cold-call`** (Merge-upgraded to amount
11), reproducible deterministically at seed 0 from a serialized state
dump.

Root cause is more general than that one piece: `selfState`
`heatAbove`/`heatBelow` evaluate against `CombatSideState.heat`, which is
a **per-fight accumulator** (`riskRewardBurst` heat costs, folded into
run Heat afterwards as `playerHeatGenerated`), not the run's actual Heat
— which is never passed into `playCombat` at all. So `heatBelow` is true
at the start of essentially every fight regardless of real run Heat, and
`heatAbove` is near-dead content. Affects **9 player pieces and 2 enemy
instances**. Fixing it needs run Heat threaded into `CombatOptions`, not
just a `triggers.ts` change.

Correction worth recording: I first described this as "combat-local
heat," implying a second Heat resource. The user pushed back correctly —
there is only one Heat; that field is this fight's pending increment to
it, and the bug is that the trigger reads the wrong quantity.
