## Goal

Implement all 9 checkpoints (A-I) from `BACKLOG.md`'s "Mods
Implementation" spec: the Mod type system, state threading, combat-scoped
and run-level hook dispatch, the 6 class passives' migration, the
granted-subroutine mechanism, reward/Shop wiring, and all 17 validated
Mods as real, working data.

## Key decisions

Confirmed with the user up front: do all 9 checkpoints in one sitting
rather than splitting across sessions (matching session 28's 5-checkpoint
Enemy Library push). Two background Explore agents then pinned down the
exact current shape of every function the plan would touch (resolve.ts's
enemy-passive dispatchers, triggers.ts's readiness check, run.ts/
encounters.ts/shop.ts's orchestration) before writing the implementation
plan, so the plan cited real line numbers and signatures rather than
guessing from the session-33 spec's prose alone.

Two real corrections surfaced only once inside the actual code, not
during scoping:

- **Checkpoint D's migration shape**: the plan called for literally
  folding the 6 class passives into the shared per-hook dispatcher
  functions. In the real code, several (Zero Day's mid-payload Heat
  waiver; Return to Sender's three distinct trigger points) don't fit
  that post-fire fold shape without changing their own behavior. Shipped
  as a gating-only migration instead — each `classId === 'x'` check
  became an `ownedModIds` membership check, call sites unchanged.
  Zero-regression safety came from a deliberate design choice:
  `resolve.ts`'s `createCombatState` auto-derives the current class's
  own exclusive Mod into `ownedModIds` whenever `classId` is set, so
  every pre-existing test/call site that only ever passed `classId` (the
  whole suite, before this session) keeps working unchanged.
- **Checkpoint G's archetype-exclusion direction**: the plan said to
  "invert" `rewardPoolForClass`'s `!ownArchetypes.has(...)` check.
  Re-reading `DESIGN.md`'s actual session-30 text against the real code
  showed the correct direction is the *same* inclusion logic
  `rewardPoolForClass` already uses (a Mod naming an archetype is only
  offered to a class whose own 2 specializations include it), not an
  inversion — the plan's own phrasing was a misreading, caught before
  writing the filter.

  Shipped without a typed-per-hook-signature catalog — `EnemyPassiveId`'s

  function-signature registry) is the actual codebase idiom for this
  "light registry, not a DSL" pattern.
- `mods.ts` (new): all 23 `ModDefinition`s (6 migrated class passives +

  `maxHeatBonus`/`modRunState`; `CombatOptions`/`CombatState` gained

## Notable problem-solving notes

- Two Explore agents run in parallel before planning (combat-scoped hook
  machinery; run-level orchestration/reward wiring) turned session 33's
  prose spec into exact, quoted, current code — this is what surfaced
  both real corrections above before any code got written, not after.
  Worth repeating for any future implementation session working from an
  engineering-scoping session's spec that predates the actual coding.
- The `createCombatState` auto-derivation trick (folding the current
  class's own exclusive Mod into `ownedModIds` regardless of what's
  explicitly passed) is the single design choice that made checkpoint
  D's migration safe against ~450 pre-existing tests that construct
  `CombatOptions`/`CombatState` directly with just `classId` set. Worth
  remembering as a pattern for any future "migrate an implicit behavior
  onto an explicit list" refactor in this codebase.
- Deliberately did not force every one of the 6 class passives into the
  shared dispatcher shape once their real call sites turned out to be
  heterogeneous (one-shot vs. persistent, mid-resolution vs. post-fire,
  1 vs. 3 trigger points) — matching this project's own repeated lesson
  (sessions 21, 27) that forcing real heterogeneous logic into one
  generic shape before it's actually needed creates risk without benefit.
