# Session 36 — 2026-08-28

`/decision-session` — designed the two systems the user flagged as
necessary before the per-class magnitude/balance pass (session 29's own
standing "next up"): a new consumable-item system (**Burners**) and the
long-undesigned **Event** node. Docs only, no code — same category as
sessions 15/17/19/21/30/31/32.

## Goal

Answer two open questions before the balance pass: whether one-off
consumable items (crib.exe's answer to StS Potions) even belong in this
design at all, and — separately, already flagged as a real must-design
item — what an Event node actually is, mechanically.

## Key decisions

Resolved live, one fork at a time, each with a recommendation offered up
front:

1. **Consumables' fit and niche**: yes, but reframed away from a direct
   StS-Potion port — as **manual, on-demand, player-activated-at-will**
   items, the one gap left by subroutines (automatic/trigger-gated) and
   Mods (passive/permanent). Named **Burners** (the user's own
   suggestion, following a "burner phone" comparison raised while
   discussing the niche) — a real disposable-phone term, precisely
   matching "single-use, spent forever on use."
2. **Activation timing**: only on the player's own turn in combat, not
   anytime mid-hand — the anytime version needs the engine's turn/hand
   loop to become pausable/resumable, the same gap already banked since
   session 24 for human-vs-AI play. Deliberately deferred, not
   half-built.
3. **Scope widened mid-session, user's own idea**: Burners aren't
   combat-only — also usable at the map level (free move, reveal, reopen
   a closed node) and in the Shop (a "coupon" — discount/reroll/rarity
   floor). Resolved as one unified item pool with per-Burner context
   tags, not three separate item systems. The map-context "reopen a
   closed node" effect directly resolves the session-9 banked
   node-bypass idea.
4. **Inventory shape**: capped, no bench/installed split — mirrors StS's
   potion-slot cap and the subroutine loadout's own slot-scarcity
   tension, unlike Mods' fully uncapped ownership (which has no such
   tension to protect).
5. **Events' paradigm**: narrative vignette + 2-4 choices, resolved
   instantly, no Cribbage played — over a mini Cribbage-mechanical
   challenge (thematically stronger but genuinely new engine work) and a
   pure reward-reveal (too weak to earn its own node type).
6. **Events' risk model — the session's most-discussed fork**: opened
   recommending full transparency (matching the project's existing
   house style, where nothing else hides numbers from the player); the
   user pushed back and landed on a genuine **mix**, per-choice rather
   than per-Event or global: `transparent`, `visibleOdds` (probabilistic
   with odds shown), and `gamble` (genuinely uncertain) coexist across
   the pool, with risk tier gating reward ceiling — the riskiest tier is
   the only place the most powerful outcomes can appear.
7. **Session scope**: at a natural stopping point (both systems' shape
   settled), asked whether to keep sketching concrete examples or wrap
   into the docs now — user chose to wrap, deferring content-authoring
   and engineering-scoping to a future session, matching the Mods
   precedent (shape → hooks → content → implementation, sessions 30-33).

## Notable problem-solving notes

- The user's mid-session pivot on Burners (combat-only → also map/shop
  context) is a good example of why broad-strokes discussion earns its
  keep before locking a shape: the initial "own-turn-only" answer was
  correct as far as it went, but stopping there would have missed a
  genuinely better system the user was already reaching for.
- Asked to justify the "always transparent" recommendation rather than
  just accepting it — worth remembering that a stated recommendation
  isn't the same as a settled decision; the user wanted the actual
  reasoning (Heat's legibility depending on it, the game's real-Cribbage
  skill identity, the project's sweep-driven balance culture) before
  weighing in, and the eventual answer (a deliberate mix) was better
  than either the recommended default or a flat rejection of it.
