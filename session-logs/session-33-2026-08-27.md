## Key decisions

Explored the actual codebase before proposing anything (`resolve.ts`'s
size, `loadout.ts`'s exact cap/install/uninstall functions,
`RunPlayerState`'s existing `material`/`rank` per-id-record pattern),
which resolved two structural questions by precedent rather than by
forcing them into live decisions:

- **File split**: `resolve.ts` is already 1595 lines. Combat-scoped hook
  dispatch stays there (same `CombatState` coupling the enemy passives
  already need); the type system and run-level dispatch + Mod data get
  new files (`mod-types.ts`, `mods.ts`), mirroring
  `subroutine-types.ts`/`subroutines.ts`.
- **Granted-subroutine tracking**: no new field on `SubroutineDefinition`
  — a new `grantedByMod: Record<string, string>` on `RunPlayerState`
  follows the exact existing shape `material`/`rank` already use for
  per-instance ownership state kept separate from static subroutine
  data.

Two genuine forks, resolved live:

1. **Content-authoring scope**: author all 17 validated Mods as real
   data in this pass, not a Phase-2-style representative subset — unlike
   Phase 2, all 17 are already fully designed, so there's no "content
   doesn't exist yet" reason to hold any back. Confirmed in one round.
2. **Class-passive migration timing**: fold the 6 existing class
   starting passives' migration into this same phase, as its own
   checkpoint — the user's explicit call ("it's work that needs to be
   done, no sense in holding off"), overriding my initial recommendation
   to defer it the way session 27 deferred the analogous question for
   the enemy registry, given real regression risk on well-tested,
   balance-sensitive code (Ghost's rework, Lock Fatigue). Kept as an
   isolated checkpoint specifically to contain that risk rather than
   folding it into new-infrastructure work.
