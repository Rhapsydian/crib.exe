## Key decisions

Resolved live, one at a time, per this project's `.claude/dev-session.md`
override:

- **Mechanism**: my first draft scoped the strategy to fights-only
  detours (Shop/Event/Safehouse "for their own sake" out of scope). The
  user corrected this directly — Shops and Events are real acquisition
  opportunities, and Safehouse's Rest extends how much of a layer is
  even reachable, with Merge a direct power increase. Revised to treat
  all node types as real, if less direct, power sources.
- **Weighting**: fights always top priority (direct, reliable). Heat-high
  *or* material-high both pull toward Safehouse; Data-high pulls toward
  Shop; Event only pulls when Heat, material, *and* Data are all low
  together (the user's own addition — a low-resource fallback gamble,
  not a general-purpose detour).
- **Rest-vs-Merge tiebreak** at a Safehouse when both Heat and material
  triggers fire at once: **Heat wins** (the user's explicit call — it's
  the run-ending resource, safety-critical in a way Merge's power gain
  isn't).
- **Scope/process**: given the small size (one traversal strategy, one
  safehouse strategy, a signature widen, CLI wiring — not a
  Mods/Burners-Events-sized arc), the user asked to implement in the
  same sitting rather than stopping at a written spec the way sessions
  30-33/36-37 did for larger arcs.

codebase):

| class | beeline | explore | opportunistic |
|---|---|---|---|
| breacher | 24.0% | 26.5% | 26.0% |
| blackhat | 33.0% | 20.0% | **26.5%** |
| saboteur | 33.0% | 51.5% | 50.5% |
| operator | 40.5% | 43.0% | 42.5% |
| warden | 33.5% | 50.5% | 43.0% |
| ghost | 21.0% | 39.5% | 36.0% |
| avg | 30.8% | 38.5% | 37.4% |

Blackhat is the clearest validation: explore's Heat fragility (session
38's own finding) tanks it to 20.0%; opportunistic's Heat-safety-reserve
protects it, landing at 26.5% (heat-maxed roughly halved vs. explore,
49/200 vs 69/200) — a real middle-ground result, not a coincidence.
Elsewhere opportunistic tracks close to explore, ahead of beeline.

**Finding 1 — the noRoute anomaly, investigated and explained (not a
bug)**: opportunistic showed a *higher* `noRouteRemains` rate than
explore for breacher/operator/ghost despite being the more
Heat-conservative strategy. Instrumented both strategies on 300 shared
seeds: opportunistic visits *more* distinct fight nodes per run than
explore (e.g. breacher 9.05 vs 7.58) while using *fewer* total moves
(19.07 vs 23.33) — because explore burns moves on every Safehouse/Shop/
Event node indiscriminately (zero closure risk, but wasted budget) and
its node selection isn't actually nearest-first (node-array order, a
pre-existing quirk), while opportunistic always takes the true shortest
path and skips non-fight nodes unless a real pull condition fires. Every
sampled noRoute-ending run closed exactly 1 fight node before ending
(matches session 20's "resilience guarantee only promises safety against
one closure" finding) — so engaging more distinct fights per run is
more independent rolls against that single-point-of-failure risk. Net
victory *counts* stay essentially level (82 vs 82 breacher, 129 vs 123
operator, 113 vs 114 ghost) — the extra engagement converts into a mix
of extra wins and extra noRoute losses, not a clean win. Not a defect —
an honest reflection of the "leaning into either extreme is a real
tradeoff" framing already in `DESIGN.md`.

**Finding 2 — banked, not acted on: does `HEAT_PER_MOVE` need bumping?**
The user asked directly. Checked before answering: for 5 of 6 classes,
movement Heat is already the dominant Heat source, but runs still end at
32-42% of `HEAT_MAX` on average via quarantine/noRoute, `heatMaxed` at
0/300 — real headroom, Heat isn't the current bottleneck. **Blackhat is
the exception and the reason not to bump it casually**: 72.7/100 average
final Heat, 26% heat-maxed rate *at the current value*, driven by a
combination of its own kit's Heat taxes (session 38's fix) and movement
compounding on top — a global bump would land hardest on the class least
able to absorb it, risking undoing last session's fix. User's call:
leave `HEAT_PER_MOVE` as-is, bank the question for the actual balance
pass, where a candidate value can be tested against the full roster
(Blackhat especially) the same empirically-tested-candidates way session
38 tuned Blackhat/Breacher, rather than picked by feel now.

## Notable problem-solving notes

- The noRoute investigation is a good example of not settling for a
  plausible-sounding guess: my first hypothesis in conversation (more
  total node engagement generally) didn't hold up against direct
  instrumentation — the real driver was *move efficiency* letting
  opportunistic reach *more* fights, the opposite of what "more
  conservative" suggested it should do. Matches this project's standing
  "empirical, not guessed" discipline.
- `exploreThenGatekeeper`'s node selection turned out not to be true
  nearest-first (iterates `graph.nodes` in array/generation order, not
  sorted by path length) — a pre-existing simplification from session 19,
  noticed while building `opportunisticTraversal`'s own genuinely
  nearest-first `nearestOf` helper. Not fixed here (out of scope, no
  behavior change requested), just noted for whoever next touches
  `exploreThenGatekeeper`.
