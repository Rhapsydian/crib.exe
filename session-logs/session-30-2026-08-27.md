# Session 30 — 2026-08-27

`/decision-session` — designed the *shape* of crib.exe's StS-relic
equivalent, named **Mods**, at the user's request, pausing the per-class
magnitude/balance pass (session 29's own "next up") to do it first. No
code — docs only, same category as sessions 15/17/19/21's engineering-
scoping sessions, but for game design rather than implementation
checkpoints, since Mods had never been designed at all before this
(session 21 explicitly deferred it to "its own future
`/decision-session`").

## Goal

Turn `DESIGN.md`'s one-line placeholder ("an expanding pool of in-run
passive items... including passives that hook into subroutine tags")
into a real design, before starting on the actual content library or
the deferred balance pass.

## Key decisions

Opened with a broad-strokes discussion (not a forced question) about
what Mods should be, informed by exploring the existing codebase —
specifically the passive-effect precedent already built for the 32-enemy
roster (session 27's light `{id, hookPoint, fn}` registry in
`resolve.ts`) as a preview of exactly the kind of infrastructure a
player-facing pool would need. Then resolved 6 concrete forks live, one
at a time, each with a recommendation:

1. **Engine mechanism**: split by effect shape rather than inventing a
   third generic system — trigger/payload-shaped Mods reuse
   `SubroutineDefinition` wholesale; everything else (tag/archetype
   affinity, stat/resource/economy modifiers, run-meta hooks) extends
   the existing enemy-passive registry to a player-side owned-Mod-id
   list. Matches the user's own framing (tag hooks, archetype hooks,
   "an additional reactive subroutine" were all named as things Mods
   should be able to do) and avoids re-litigating the premature-
   genericization calls sessions 21 and 27 already made correctly.
2. **Reward-slot structure**: additive, not competing — elite/gatekeeper
   wins grant a Mod choice *in addition to* the existing subroutine
   reward, mirroring StS's own elite-guarantees-a-relic-plus-the-normal-
   card-reward shape.
3. **Pool scoping**: universal by default (any class can find any Mod),
   with one exception the user raised unprompted: a Mod leaning heavily
   on a specific archetype gets excluded from a class's pool when that
   archetype isn't one of the class's 2 specializations, to avoid
   guaranteeing a structurally dead reward — the same concern that
   drove the Neutral Archetype (session 28). Implemented as the existing
   `ClassDefinition.archetypes` check subroutine rewards already use,
   inverted into an exclusion.
4. **Ownership cap**: uncapped, matching StS relics — the subroutine
   loadout's cap (session 7) exists specifically to protect an
   ordering/slot-scarcity decision Mods don't have (no install/bench
   split, no ordering), so that reasoning doesn't transfer. The user's
   own framing: "the opportunity cost for them is baked into their
   acquisition," not an equip limit.
5. **Shop structure**: two independent slates (existing subroutine
   slate unchanged, plus a new Mod slate), separately rerollable, one
   shared Data pool — not one combined slate/reroll, since a subroutine
   reroll and a Mod reroll are different gambles over different pools.
6. **Class starting passives**: migrate onto the new Mod infrastructure
   as class-exclusive Mods (granted at run start, never in the general
   pool) — the user's own call, made explicitly ("that is what they
   are, just only acquirable by selecting a given class"), making
   `DESIGN.md`'s existing "same role as StS's class-starting relics"
   comparison literal rather than analogical.

Two low-controversy corollaries stated directly rather than forced into
their own questions, following the user's own reasoning: Mods are
unique (no duplicates, no Merge interaction needed) and use
common/uncommon/rare rarity mirroring subroutines, with power/build-
definition scaling by rarity (the user's own point, stated up front).

## Notable problem-solving notes

- Exploring the actual `resolve.ts` code before opening the design
  conversation paid off directly: the enemy-passive light registry
  (built session 27, a phase before the player side needed it) turned
  out to be almost exactly the right shape for half of what Mods need,
  which made "reuse two existing mechanisms, don't build a third" a
  much stronger recommendation than it would have been from design
  intuition alone.
- The archetype-exclusion pool-scoping rule (decision 3) is a case
  where a "mostly settled" answer from the user still had a real edge
  worth surfacing and resolving explicitly, rather than treating "largely
  universal" as fully resolved on its own.
