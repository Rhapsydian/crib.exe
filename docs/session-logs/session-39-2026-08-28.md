## Key decisions

Resolved live, one at a time, per this project's `.claude/dev-session.md`
override:

- **Mechanism**: my first draft scoped the strategy to fights-only
  detours (Shop/Event/Safehouse "for their own sake" out of scope). The
  user corrected this directly — Shops and Events are real acquisition
  opportunities, and Safehouse's Rest extends how much of a layer is
  even reachable, with Merge a direct power increase. Revised to treat
  all node types as real, if less direct, power sources.
- **Weighting**: fights always top priority (direct, reliable). Heat-high
  *or* material-high both pull toward Safehouse; Data-high pulls toward
  Shop; Event only pulls when Heat, material, *and* Data are all low
  together (the user's own addition — a low-resource fallback gamble,
  not a general-purpose detour).
- **Rest-vs-Merge tiebreak** at a Safehouse when both Heat and material
  triggers fire at once: **Heat wins** (the user's explicit call — it's
  the run-ending resource, safety-critical in a way Merge's power gain
  isn't).
- **Scope/process**: given the small size (one traversal strategy, one
  safehouse strategy, a signature widen, CLI wiring — not a
  Mods/Burners-Events-sized arc), the user asked to implement in the
  same sitting rather than stopping at a written spec the way sessions
  30-33/36-37 did for larger arcs.

Blackhat is the clearest validation: explore's Heat fragility (session

**Finding 1 — the noRoute anomaly, investigated and explained (not a
bug)**: opportunistic showed a *higher* `noRouteRemains` rate than
explore for breacher/operator/ghost despite being the more
Heat-conservative strategy. Instrumented both strategies on 300 shared
seeds: opportunistic visits *more* distinct fight nodes per run than
explore (e.g. breacher 9.05 vs 7.58) while using *fewer* total moves
(19.07 vs 23.33) — because explore burns moves on every Safehouse/Shop/
Event node indiscriminately (zero closure risk, but wasted budget) and
its node selection isn't actually nearest-first (node-array order, a
pre-existing quirk), while opportunistic always takes the true shortest
path and skips non-fight nodes unless a real pull condition fires. Every
sampled noRoute-ending run closed exactly 1 fight node before ending
(matches session 20's "resilience guarantee only promises safety against
one closure" finding) — so engaging more distinct fights per run is
more independent rolls against that single-point-of-failure risk. Net
victory *counts* stay essentially level (82 vs 82 breacher, 129 vs 123
operator, 113 vs 114 ghost) — the extra engagement converts into a mix
of extra wins and extra noRoute losses, not a clean win. Not a defect —
an honest reflection of the "leaning into either extreme is a real
tradeoff" framing already in `DESIGN.md`.

**Finding 2 — banked, not acted on: does `HEAT_PER_MOVE` need bumping?**
The user asked directly. Checked before answering: for 5 of 6 classes,
movement Heat is already the dominant Heat source, but runs still end at
32-42% of `HEAT_MAX` on average via quarantine/noRoute, `heatMaxed` at
0/300 — real headroom, Heat isn't the current bottleneck. **Blackhat is
the exception and the reason not to bump it casually**: 72.7/100 average
final Heat, 26% heat-maxed rate *at the current value*, driven by a
combination of its own kit's Heat taxes (session 38's fix) and movement
compounding on top — a global bump would land hardest on the class least
able to absorb it, risking undoing last session's fix. User's call:
leave `HEAT_PER_MOVE` as-is, bank the question for the actual balance
pass, where a candidate value can be tested against the full roster
(Blackhat especially) the same empirically-tested-candidates way session
38 tuned Blackhat/Breacher, rather than picked by feel now.

## Part 2 — the balance pass begins, then pivots into methodology and a real engine gap

The session didn't end at the close-out above — the user asked to start
the balance pass on the remaining classes right after, and it grew into
a much bigger arc than "fix a few numbers": a real methodology critique,
a new piece of permanent diagnostic infrastructure, and a genuine
difficulty-curve engine gap, fixed and empirically tuned.

### Null Session: found, chased, then mostly dissolved

Matchup-swept Saboteur/Operator/Warden/Ghost against all 12 gatekeepers
(100 seeds each, bare starting kits, `sweep.ts`'s `enemy` mode shape),
then widened to all 6 classes for the worst outliers. Two real findings,
distinguished from the already-accepted "Firewall Prime/Incident
Response are broadly hard, left alone" call (session 38): **Null
Session** was a sharp *bimodal* outlier — Operator 96% vs. 0-8% for
5 of 6 other classes — not a spread-the-pain gatekeeper. **Ghost** had a
real gap against Exploit/Malware-leaning gatekeepers (Adaptive Threat 0%,
Total Compromise 17%) despite dominating Root-heavy ones.

Traced Null Session's mechanism precisely via ablation (drop each kit
piece, re-sweep): **Zero Trust alone** was the entire problem — its
`instantCounterPush` amount (`CAPPED.rare` = 18) wipes 36% of the win
threshold in one reactive proc; Cron Job/Full System Compromise/Circuit
Breaker barely moved the needle (confirmed against Ghost Process, which
shares the same tempo-denial pair and is perfectly winnable). Tested a
bespoke, Null-Session-only tempered copy (amount 18 → 11 =
`UNCOMMON.burst`) that fixed the near-0% wall without touching the
shared pool piece (so Firewall Prime's own already-decided matchup stays
untouched) — **but never shipped it**, because the next step (a
realistic-state re-test) showed it probably wasn't needed at all.

### The methodology correction that mattered most

Asked directly how these matchup tests were actually run: bare
`CLASS_STARTING_LOADOUTS`, `playCombat`'s own dumb baseline AI
(`discardLowestTwo`/`playLowestLegal`) on *both* sides — not the real
skill-dial AI every actual gatekeeper encounter uses via
`strategiesForFight`. The user pushed back hard on testing worst-case
floors instead of real play: "isn't the balance sweep supposed to be
actually playing the game, all of its pieces?" Investigating that
question surfaced a bigger, previously-unstated fact: **every real fight
in this game, and every balance sweep since session 27, has the player
side playing Cribbage at the dumbest possible level** while enemies scale
up by tier/layer (`strategiesForFight`'s comment: "Only the enemy...
gets a skill-derived strategy"). Session 24 tested giving the player
real skill once, as a side investigation; it never became the default.

Built real infrastructure instead of another one-off script:

- **`onBeforeGatekeeperFight`** (`run.ts`): an additive, zero-effect
  observational hook, fired once right before each gatekeeper fight
  resolves, snapshotting the player's *real* accumulated `RunPlayerState`
  at that exact moment (whatever a real `playRun()` actually picked up —
  installed loadout, bench, Mods, Burners, Data) plus the
  `layerIndex`/`fightsResolved` a real `resolveFight` call would use.
  Verified with a dedicated test proving exact fire count/timing and
  that layer 1's capture is genuinely pre-acquisition (still exactly the
  3-piece starting kit).
- **`scripts/gatekeeper-check.ts`** (new, permanent): consumes that hook.
  Deliberately does *not* try to average a loadout across seeds (acquired
  content can't be meaningfully blended into one coherent object) —
  instead runs N real seeds per class (`opportunisticTraversal` + the
  usual legal-not-good defaults), captures every gatekeeper actually
  reached, and re-fights each captured *real* state in isolation against
  the real production skill-dial enemy AI at a chosen player skill
  (0.75 = matches the gatekeeper's own base skill, "fair"; 1.0 =
  "strong"), aggregating win rate per (class, gatekeeper, player skill)
  and, after a follow-up ask, per layer too.

**The 300-seed realistic re-sweep reversed the Null Session finding
almost entirely** — 93.5%/93.5%/64-71%/100%/65-69%/82-87% across the 6
classes, once real acquired power was in the picture. The near-total
lockout was mostly an artifact of testing bare day-one kits against a
worst-case floor. **The Zero Trust tempering fix was shelved, not
shipped** — it may not be needed now that real data exists instead of a
guess. Firewall Prime turned out to be the real remaining outlier
(Warden specifically: 4.5-5.7%, flat regardless of player skill) —
flagged, not yet acted on.

### The per-layer difficulty curve: a real, structural engine gap

Asked directly whether per-layer difficulty scaling had been
implemented. It hadn't, beyond a small skill-dial step
(`LAYER_SKILL_STEP` = 0.03) — `DESIGN.md`'s "meant to be very
challenging for the layer it's presented at" was pure authoring intent,
enforced by nothing. `gatekeeper-check.ts`'s new by-layer aggregation
(added specifically to check this) confirmed it empirically and
unambiguously, every class: layer 1 was the *hardest* tier (77.4%
aggregate) and it got progressively easier (L2 88.4%, L3 98.8%, L4
93.9%) — backwards from intent, because player power compounds across
layers faster than the tiny skill-dial step could ever offset.

Built a real fix, resolved live one decision at a time per this
project's `.claude/dev-session.md` override:

- **Magnitude scaling, not just skill** — a per-layer multiplier applied
  to enemy payload magnitudes at combat-resolution time (never baked
  into the static roster data). Multiplicative, not additive (a flat
  bonus would hit low- and high-magnitude payloads unevenly). Reused
  `merge.ts`'s existing magnitude-dispatch machinery
  (`improvedPayloadMagnitude`) rather than duplicating the payload-kind
  switch — refactored into a shared `transformPayloadMagnitude` core,
  with the new multiplicative `scaledPayloadMagnitude` as a sibling to
  the existing additive one.
- **Two different shapes, the user's own call**: regular/elite (which
  can legitimately appear at several layers) scale *live*, computed
  per-encounter from one shared tier-agnostic formula
  (`enemyMagnitudeScaler`, pinned to no scaling during the opener
  window). Gatekeepers (which never repeat across layers) instead get an
  **explicit, individually authored `magnitudeScaler` field** on
  `EnemyDefinition` — seeded uniformly per layer as a starting point, but
  a real standalone tuning knob per gatekeeper from here on (e.g.
  Firewall Prime, already the roster's hardest fight, is flagged as an
  obvious future candidate to dial back rather than up).
- **Confirmed wanted, explicitly deferred**: independent per-side
  initiative/win-gauge thresholds (asymmetric Breach/Containment
  difficulty), motivated by both this scaling work and future
  meta-progression. Currently `CombatOptions`/`createCombatState` share
  one threshold across both sides — real plumbing work, scoped as its
  own future pass rather than bundled in here.

**Tuned empirically, not guessed**: first candidate step (0.15/layer,
gatekeepers seeded 1.0/1.15/1.3/1.45) narrowed the layer-1-vs-4 gap but
didn't close it — L4 still an easier 85.6% win rate against L1's harder
77.4% (win rate is inverse to difficulty: lower = harder). Re-swept at
double the step (0.3/layer, 1.0/1.3/1.6/1.9): L4 dropped to 76.9%,
landing at parity with L1's 77.4% (within noise, given L4's smaller
surviving-run sample size) — the real target: a run's final stretch
should be at least as hard as its start. Landed here. Layer 3 remains a real, separate
outlier (94.1%, essentially unmoved by either step) — it was already the
easiest layer before any scaling, so it's very likely a genuine
kit-design weakness (its own trio: Total Compromise/Adaptive
Threat/Silent Corruption), not something a multiplier can fix — flagged
for a future content-level look, not acted on here.

Also, at the user's request: **removed `maxHands`/`FIGHT_MAX_HANDS`
outright** (`combat.ts`/`encounters.ts`/`scripts/sweep.ts` and every
test that referenced it) — `HARD_RESOLUTION_HAND` (session 27) has
unconditionally forced every real fight to resolve by hand 20 since it
shipped, so the old bound had been genuinely vestigial the whole time,
"left in place as a defensive outer bound" rather than removed at the
time. Two tests whose entire premise was forcing early exhaustion via an
artificially tiny `maxHands` had no way to construct that scenario
anymore — rewritten to assert the real current behavior instead of
removed outright. Found and fixed two stale comments along the way (a
specific hand-count claim and an escalation-start-hand claim, both
predating later retunes that were never reflected back into their own
comments).

## Part 3 — the per-class balance pass, against a real external benchmark

## Goal

Continued straight from Part 2's own close-out: the user compared
crib.exe's numbers to Slay the Spire's published ascension-0 full-run
win rate (9-15% for a new player) and judged crib.exe's own numbers —
even after the per-layer scaler — way too high given how limited real
skill expression currently is (Cribbage play, map pathing, loadout
selection). That became a concrete, external target for the per-class
balance pass, rather than "make the numbers look reasonable."

## Key decisions

A fresh full-run sweep (post-scaler) put the average at ~20.8% — down
from ~31-38% pre-scaler, but Saboteur (24.3%), Operator (20.7%), and
Ghost (28.7%) were still well above the 9-15% band; Warden (26.3%) too.
Breacher (11.7%) and Blackhat (13.3%) were already inside it, unplanned,
purely from the scaler. Resolved live, one class at a time, same
isolate-then-fix discipline as every prior balance fix in this project
(Blackhat/Breacher session 38, Null Session/Firewall Prime earlier this
session):

- **Warden**: offered dealer-gating first (session 25's own first
  proposed fix for Feedback Loop, already flagged as a suspect), found
  it too weak alone (26.3% → 23.7%), combined with a magnitude cut to
  reach the band (0.5, dealer-gated → 13.7%) — but asked to explain the
  mechanism led the user to notice a real design overlap with Ghost's
  Return to Sender (which already hooks HoT ticks). Took the bigger
  redesign instead: reciprocal HoT/DoT amplification. First attempt
  scaled the bonus proportionally to the triggering tick's own size
  (matching Return to Sender's own ratio) — this compounds
  multiplicatively across a match's many ticks and made Warden
  *stronger* than the original unfixed passive at a seemingly modest
  ratio (0.5 → 33.0%, higher than 26.3%). Corrected to a flat per-tick
  step (linear growth, no runaway) once the user clarified they'd meant
  a flat bonus, not a scaled one — landed at 0.15.
- **Saboteur**: same flat-bonus-stacking shape as Warden's original
  problem, found immediately by pattern-matching. Straightforward
  magnitude retune, no overlap concern, confirmed and locked in one
  round.
- **Operator**: a structurally different mechanic (permanent, compounding
  loadout mutation rather than a per-tick credit) — investigated before
  touching any number, found Primed's trigger-easing half was a
  complete no-op for Operator's real kit (Precision Strike's
  `occurrence:instant` trigger has nothing to ease), so the magnitude
  half was carrying 100% of the real effect. The floor (0) collapsed the
  class entirely, a much starker result than either prior fix's floor —
  flagged explicitly before proposing a smaller relative cut. User asked
  for one specific alternate data point (2, not just the recommended
  1.5) before picking 1.5 for the extra headroom.
- **Ghost**: neither of its two real credit sources (Idle Process,
  Return to Sender) alone reached the band — Return to Sender at a full
  0 still left Ghost at 17.0%, and Idle Process at 0 collapsed Ghost to
  0.0% (avgLayers 0.01), reconfirming session 28's own original
  finding about that piece's load-bearing role. Halved both together.
- **The Zero-Sum coupling**: re-running a full 6-class sweep to report
  back (per the user's own explicit ask, "run the sweep") surfaced a
  real, unexplained discrepancy — Warden's number had moved between two
  identical-looking runs. The user asked directly whether this could
  just be noise given the same seeds, which prompted actually bisecting
  it commit by commit (`git checkout <sha> -- .`, re-sweep, repeat)
  rather than assuming — isolated to the exact Operator commit despite
  its diff touching nothing Warden-related. Root cause: Zero-Sum's own
  enemy passive reused Operator's exact tuning constants unconditionally.
  The user asked directly whether the two should use different
  constants; agreed and split them, seeded at the pre-fix values so the
  split was pure decoupling, not an additional balance change.

## Part 4 — Firewall Prime redesign, player/enemy skill decoupling, Basic Cribbage mode, and the roster-wide dead-mechanism audit

### Goal

Part 3's deferred list named Firewall Prime (esp. vs. Warden, 4.5-5.7%)
as the next real outlier. Taking that on surfaced a chain of deeper
methodology problems — what "the player's skill" even means in a
diagnostic, whether a full-run benchmark and a single-gatekeeper number
measure the same thing, and whether the enemy roster's shared-pool
content was actually alive — each investigated properly rather than
patched around, per this project's own standing rigor.

### Key decisions

1. **Redesign Firewall Prime's Zero Trust and Redundant Backup, not just
   retune Warden.** Ablation showed Zero Trust was the dominant piece
   (95.8% win rate for Warden without it vs. 0% with it); a hard fire cap
   either no-op'd or trivialized the matchup for every class, so it was
   redesigned as a self-limiting linear decay (new generic
   `magnitudeDecayPerFire`/`magnitudeFloor` mechanism) instead. A second
   investigation found Redundant Backup's `hot` payload credits
   `mitigationBanked` its *full* `amountPerTick*duration` at cast time
   (20, more than 2x Circuit Breaker's own threshold) — tuned down to a
   bespoke `redundant-backup-firewall-prime` copy (credit=8). Net effect
   on Warden specifically: 0.0% → 11.8%, real progress but not fully
   resolved (a credit=12 compromise helps Breacher/Blackhat/Operator more
   but pulls Warden back under 9% — the exact value is still an open
   tradeoff, see Deferred below).
2. **Full-run and per-gatekeeper numbers are not the same measurement,
   and must not be silently conflated.** A user question ("how can
   breacher have 13.5% full-run and 80% at layer 4?") exposed that
   `gatekeeper-check.ts`'s per-gatekeeper win rate is an isolated re-fight
   with a fresh seed and a chosen skill dial — explicitly documented as
   *not* replaying what a real run's own resolution decides
   (`onBeforeGatekeeperFight`'s own doc comment already said so). Built
   `scripts/layer-funnel.ts` as the real, permanent fix: reads
   `layersCompleted`/`outcome` straight off real `playRun()`s, asserts
   `layersCompleted>=4` exactly equals `outcome==='victory'` for every
   class (verified true), never conflates the two measurement shapes
   again.
3. **Player skill and enemy skill must never be interlocked, permanently
   — a standing engine rule, not a one-off fix.** Discovered the
   project's own full-run benchmark comparison had been running the
   player at `playCombat`'s dumb floor baseline this entire session
   (`discardLowestTwo`/`playLowestLegal`, no skill dial at all) while a
   separate diagnostic used a 0.75-1.0 skilled player — two different
   "players" being compared to the same StS benchmark. Fixed by adding
   `run.ts`'s own `playerSkill` option, threaded through
   `encounters.ts`'s `strategiesForFight` so it composes with (never
   replaces) the enemy's own real per-fight `enemySkill()` scaling.
   Opt-in only — `undefined` still means the existing baseline, so no
   script's behavior changed silently.
4. **0.85 is the new standing player-skill default for diagnostic
   scripts, calibrated not guessed.** Real enemy skill tops out at 0.84
   (layer-4 gatekeeper, `enemySkill()`'s own formula) and never reaches
   the dial's 1.0 ceiling at all. A pure-Cribbage skill-vs-skill
   calibration table (built on `basic-cribbage.ts`, see decision 5) shows
   a same-skill mirror match always nets ~50% regardless of level, so
   0.85 was chosen specifically to mirror the *hardest real enemy's own
   skill* — assumes the player can hang with the toughest AI on raw card
   skill alone, pushing any remaining win/loss disparity onto loadout
   mechanics where it belongs. `gatekeeper-check.ts`, `sweep.ts`, and
   `layer-funnel.ts` now default to it; `run.ts`'s own `playerSkill`
   option stays opt-in with no engine-level default, per decision 3.
5. **Basic Cribbage is a planned alternate game mode and its engine code
   is never scratch, full stop.** The first attempt at the calibration
   table went through `playCombat` with empty loadouts and returned 0%
   for side A in every cell — `playCombat`'s win condition is a separate
   `winGauge` fed only by subroutine/Mod/passive effects
   (`creditWinGauge`), never raw score, so an empty-loadout match never
   resolves by score at all. Rebuilt on `game.ts`'s real primitives
   instead (`playOneHand`/`playHands` gained per-side strategy support).
   Mid-build, the user revealed this exact tool (session 26's original
   race-to-121 cross-matrix) had been explicitly requested as permanent
   code once before and was lost anyway — built as "a scratch driver,"
   deleted per this project's own scratch-script convention, with only
   its findings preserved in BACKLOG.md. Root cause: the instruction to
   retain it was only ever spoken, never written into any durable record
   (no code comment, no BACKLOG.md note, no memory entry) — the *opposite*
   convention (scratch gets deleted) survived precisely because it *was*
   documented repeatedly. Fixed with triple redundancy this time: a
   project memory entry, a BACKLOG.md "NEXT SESSION" note, and a code
   comment on `game.ts` itself. `src/engine/basic-cribbage.ts`
   (`playBasicCribbageGame`) now ships as real, tested, committed engine
   code — independent `playerSkill`/`enemySkill` options (never
   interlocked, matching decision 3), skunk/double-skunk detection.
6. **Full 32-enemy roster audit for dead mechanisms — scoped fix now,
   broader initiative banked.** A background research agent (verified
   afterward against the actual source, not trusted blind) found 7 dead
   Heat-gated trigger instances across 9 enemies — Corrupted Cache,
   Payload Multiplier, Overclock, Air Gap (x2), Backchannel (x2) — all
   with the same root cause: enemies never accumulate Heat at all (the
   only Heat-raising pool piece, Payload Multiplier, requires Heat
   already above threshold to fire, so no pool piece can ever be the
   first mover). The user's own framing reframed the fix: the roster's
   100%-shared-pool content was always meant to allow bespoke enemy-only
   pieces (DESIGN.md), never actually used since the session-27 draft —
   the dead Heat pieces are a symptom, not the root problem. Explicit
   scope decision: fix the 7 broken slots now with a real
   `ENEMY_ONLY_SUBROUTINES` catalog (`enemy-subroutines.ts`, never
   reachable through player Merge/Shop/rewards); bank "give the rest of
   the roster real bespoke content" as its own future initiative in
   BACKLOG.md rather than absorb it into this fix.

### Notable problem-solving notes — the background-task infra saga

This part of the session spent a genuinely large amount of real time
fighting this environment's background-task execution rather than the
actual analysis, and it's worth recording precisely what was learned so
the next long-running sweep doesn't repeat the same dead ends:

- **Running several long tasks with explicit `run_in_background: true`
  in parallel is unreliable in this environment.** 6 concurrent
  `layer-funnel.ts` invocations (2 skill levels + 4 ablations) made real
  progress for a while, then went completely silent for 15+ minutes at a
  time while still reporting `status: running` -- repeatedly, across
  several wakeup cycles.
- **The apparent hang was real (in the sense that no more output ever
  came without intervention), but the underlying computation was not
  slow.** A direct, synchronous timing test -- 300 seeds of one class,
  run in the foreground with nothing else competing -- completed in 33
  seconds. The bottleneck was entirely in how this environment schedules
  or captures long-lived explicitly-backgrounded processes, not in the
  engine.
- **A single combined script (all 15 configs sequential in one process)
  explicitly backgrounded showed the same pattern** -- a fast burst,
  then long silences -- so the problem was not multi-process contention
  specifically, it was explicit backgrounding itself.
- **The fix that actually worked**: run each configuration as a
  direct, synchronous foreground `Bash` call (no `run_in_background`
  flag at all), sized so it usually completes within the tool's own
  timeout. When one occasionally still exceeded the timeout and
  auto-migrated to background on its own, it reliably finished anyway --
  the failure mode was specific to processes *launched* as background
  from the start, not to backgrounding as a state. 14 of 15
  configurations completed this way with no further issues; only one
  had to be retried after an early, overly-aggressive kill (see below),
  producing a harmless duplicate block in the scratch file that was
  caught and excluded before the report was written.
- **One real mistake along the way**: after switching to the
  foreground-then-auto-migrate pattern, a single config that had
  auto-migrated was killed prematurely, assuming it had hit the same
  stall -- it had not; a later, calmer look showed it would have
  finished on its own. Re-running it wasted time but not correctness
  (the underlying computation is fully deterministic, so the retry
  produced byte-identical results). Worth remembering: `status: running`
  plus no *new* output is not, by itself, proof of a real stall --
  especially right after a strategy change, give it one more real wait
  before intervening again.
- **Takeaway for future sessions**: for any future multi-run sweep in
  this repo, default to direct synchronous foreground calls, one
  configuration at a time (or as many as comfortably fit under a
  generous but bounded timeout), rather than launching several
  `run_in_background: true` tasks in parallel -- the latter has now
  failed reliably twice in this session (once for
  `cribbage-skill-matrix.ts`, once here) and the former has worked
  every time it's been tried.
