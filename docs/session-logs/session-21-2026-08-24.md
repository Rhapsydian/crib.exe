# Session 21 — 2026-08-24

`/decision-session`-style engineering scoping (same category as sessions
15, 17, 19) — turning `BACKLOG.md`'s one-paragraph Phase 4 sketch
(meta-progression) into a real spec for a future `/dev-session`, still no
code. Worked through three decisions live, one at a time.

**Scope boundary.** Phase 4's original sketch bundled four things —
classes, subroutine unlock pool, Ascension difficulty, in-run passive
items — at wildly different design-readiness. Classes (sessions 8/11/12/
13) and Subroutine Acquisition (session 7) are fully designed; Ascension
and the expanding passive-item pool are still "broad strokes only," never
given a real design pass. Building either now would mean doing game
design mid-implementation-scoping, breaking the project's own convention
that design happens in `/decision-session` and implementation happens in
`/dev-session`. Landed on splitting Phase 4 down to Classes + Acquisition
only, pushing Ascension and the passive pool to their own future
`/decision-session`, folded into Phase 5 alongside other undesigned
content. Confirmed in one round.

**Data's source.** Re-reading `DESIGN.md`'s Subroutine Acquisition
section surfaced a real, previously unnoticed gap: it names Data as the
shop's currency but never says how the player earns it — not an
implementation detail glossed over, an actual undesigned mechanic.
Recommended and confirmed: Data awarded automatically on every combat
win, scaled by encounter tier via Phase 3's `rewardTier` stub (already
added specifically for this), the same tier-scaling shape Heat's loss
formula already uses — independent of the subroutine-reward choice, not
traded off against it.

**Cross-run persistence.** Nothing through Phase 3 has any concept of
state surviving between separate `playRun()` calls, but Phase 4's own
scope carries a designed class unlock order (session 13) and the broader
Meta-Progression section assumes persistent unlocks generally. Building a
real save/profile layer (serialization, storage, unlock-progress
tracking) would be a meaningfully sized new engineering surface no
session has ever scoped. Recommended and confirmed: stay stubbed — all 6
classes ship immediately selectable as a run-setup parameter, unlock
order recorded as intended future gating rather than enforced, same
treatment Phase 3 gave Merge/Shop and Phase 2 gave its representative
subroutine set.

Two calls made and stated rather than forced into questions, since the
codebase's own precedent already pointed one way: the reward pool reuses
the real 18 starting-loadout subroutines from session 12 as-is (each
archetype already has 3 distinct named subroutines across sibling
classes, plus the 6 universal Cantrips) rather than authoring new content
this phase; and the 6 starting passives get hand-coded as discrete
combat-resolution hooks rather than a generic passive framework, since
they're heterogeneous one-offs and building generic infrastructure for
Phase 5's not-yet-designed passive-item pool would be speculative.

Recorded the two closed design gaps in `DESIGN.md` (Subroutine
Acquisition's new "Earning Data" note; Architecture's new "No cross-run
persistence yet" note) plus a scope-note pointer in Meta-Progression.
Expanded `BACKLOG.md`'s Phase 4 into a full 6-checkpoint spec (A: class
type system & content — including finally authoring the real 18
subroutines as data, not just `DESIGN.md` prose; B: starting passives; C:
Data & combat rewards; D: bench & installed loadout; E: duplicate
material & Merge; F: Shop wiring), matching the density of Phases 1-3.
Also folds in what used to be a separate "content pass" direction (wiring
the real 18 subroutines) as part of Checkpoint A, since Phase 4 needs
them to exist as real data regardless. Phase 5 gained a short note owning
Ascension and the passive-item pool as future design work.
