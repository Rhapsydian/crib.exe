# Session 19 — 2026-08-24

`/decision-session`-style engineering scoping (same category as sessions
15 and 17) — turning `BACKLOG.md`'s one-paragraph Phase 3 sketch (map/run
structure) into a real spec for a future `/dev-session`, still no code.
The biggest-scope decision session since session 3, and the first to
meaningfully revise `DESIGN.md` after it went "clear" at session 13.

Worked through five decisions live, one at a time:

**Headless, no rendering.** Phase 3 stays a pure `src/engine/` graph —
nodes, edges, layers, traversal — tested by script, zero SVG/DOM, same
split Phase 1 drew for cards and Phase 2 drew for combat. `DESIGN.md`'s
"reads as an actual network diagram" goal moves to a future UI phase.
Confirmed in one round.

**Real 4-layer generator, no artificial content-partial split.** Unlike
Phase 2's subroutine catalog, a parameterized map generator costs the
same to build at toy scale or real scale, so there's no equivalent of
"defer tuning 15 more subroutines" — build and test at the real 4-layer
scale from the start. Confirmed in one round.

**Node types.** Merge (needs Phase 4's duplicate-material/acquisition
system) and Shop (needs Phase 4's Data currency) and Event (undesigned)
all get included anyway, as **stub node types** — structurally present
now, real payoff wired in once their supporting systems exist. The user
raised a design question mid-round: should Merge combine with a
StS-camp-style Rest option, or stay separate, given the map (unlike StS)
allows revisiting nodes? Landed on combining them into one **Safehouse**
node (working name) offering Rest (real, since Heat is being implemented
this phase) or Merge (stub) as an either/or choice — with the trade-off
preserved by making the node go **inert after its first resolved
encounter** rather than relying on being unable to physically return to
it, since the latter breaks under free movement. User generalized this to
all three stub types: Safehouse, Shop, and Event all go inert after one
encounter, exactly like fight nodes — one uniform rule, not a special
case.

**Heat implemented, real Phase 2 combat wired into fight nodes.** Phase 3
builds the Heat resource for the first time and resolves fight nodes by
actually calling Phase 2's `playCombat()` (small representative
subroutine set, not the real 18), not an injected win/loss stub — gives
Phase 3 a genuine end-to-end, script-testable exit criterion. Confirmed
in one round, explicitly for the sake of keeping the whole engine
testable by script.

**Movement model — the session's real design pivot.** Opened by asking
whether backtracking (banked since session 18) should ship now or defer.
The user pushed back that deferring wasn't clearly right, since without
some way to route around a closed node, closing *any* node could be
run-ending — and asked to discuss the shape of backtracking before
deciding. That discussion surfaced two very different mechanics hiding
under one word: a cheap "eject back to where you came from" case needing
no backtracking machinery at all, versus a real "retreat through
already-cleared nodes to reach an ancestor junction" case. Before settling
between them, the user proposed going further than either: a genuinely
free-roam map, FTL-flavored — the player has a position on a persistent
node graph and can move along any edge, any direction, any number of
times, with movement itself carrying real pressure (a flat Heat cost per
move) rather than being free. This single mechanic turned out to subsume
three separate open threads at once: it *is* what session 18's banked
backtracking-pressure-valve idea actually was; it reframes session 9's
redundancy requirement from branching-tree redundancy into
graph-resilience (gatekeeper stays reachable from wherever the player is,
as nodes close); and it removes "backtracking" as a distinct capability
needing its own design, since movement is just movement. Layers stay a
real structural boundary — each is its own free-roam graph with its own
gatekeeper as exit — but crossing a gatekeeper is **one-way**, confirmed
separately, mirroring FTL's own sector model and keeping run state
bounded across the 4 layers.

One more node type fell out of implementing this: reviewing the node-type
list, the user asked whether a minor "stepping stone" type was needed.
Landed on **Relay** — a 5th node type with no encounter at all, always
passable, existing purely so map generation can add connectivity/
redundancy without inflating fight/reward density, and so the flat
per-move Heat cost has a pure form (moving without an encounter attached,
sharpening the FTL-style route-planning trade-off). Confirmed in one
round.

**Exclusive-branch junctions** (the other idea banked since session 18)
got its own explicit close-out after being swept into the backtracking
discussion earlier without a real answer: confirmed deferred to Phase 5,
now reframed under free-roam movement as a future edge-removal event
rather than a node property, and no longer load-bearing for the soft-lock
problem the way it was originally flagged.

Rewrote `DESIGN.md`'s Map & Run Structure section (free-roam/one-way
movement model, closed-vs-inert node-state distinction, the 5 Phase 3
node types replacing the old bare "a Merge node" mention) and Resources
section (the new flat per-move Heat source alongside the existing
duel-loss-margin formula). Expanded `BACKLOG.md`'s Phase 3 section into a
full 6-checkpoint spec (A: graph data model & node types, B: layer
generation with a resilience guarantee, C: Heat resource, D: traversal/
movement, E: node encounter resolution, F: run orchestrator), matching
the density Phases 1 and 2 used. Still docs-only.
