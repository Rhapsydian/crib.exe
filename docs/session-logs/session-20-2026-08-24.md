`/dev-session` implementation of Phase 3 (network-map/run structure),

**Pre-checkpoint touch-point**: reading `combat.ts` closely revealed the
plan's assumption was wrong — `CombatResult` returning a `finalBreachContainment`
field would have carried zero margin-of-loss information, since
Breach/Containment stops dead at exactly 0 or 100 with no overshoot.
Fixed by tracking the running **peak** value reached during the match
instead (`peakBreachContainment`) — purely additive, 101/101 existing
tests unaffected.

**Checkpoint A** (`map-types.ts`): `NodeType`, `NodeState`
(unresolved/inert/closed), `MapNode`/`MapEdge`/`LayerGraph`/`RunPosition`,
`createNode()` (Relay nodes start already inert). 104 tests.

**Checkpoint B** (`map-gen.ts`): `generateLayer()` — a random-attachment
spanning tree plus extra edges, then a generate-then-verify pass
guaranteeing the gatekeeper stays reachable from the entry after removing
any single other node, repaired via bypass edges when it doesn't. Added
`neighborsOf`/`isReachable` as shared BFS primitives in `map-types.ts`.
Verified the resilience guarantee directly across 25 seeds at real scale
(12 nodes). 116 tests.

**Checkpoint C** (`heat.ts`): `addHeat()` and `heatFromLoss()`. Initially
shipped with `heatFromLoss` only handling a `'regular'` tier — a mistake,
corrected later this session (see below). 124 tests.

**Checkpoint D** (`traversal.ts`): `legalMoves()`/`move()` — free-roam,
closed nodes never legal. 131 tests.

**Checkpoint E** (`encounters.ts`): `resolveEncounter()`, the first place
Phase 3 calls Phase 2's real `playCombat()`. Mid-checkpoint, the user
caught that dropping the `'elite'` Heat tier in checkpoint C was wrong —
`DESIGN.md`'s Heat formula always named three tiers (regular/elite/
gatekeeper), and session 19's node-type list simply never included an
`eliteFight` node type to go with it, a scoping gap rather than a
decision to cut it. Restored properly: `eliteFight` added to
`NodeType`/`map-gen.ts`'s filler weights, `heatFromLoss` back to
tier-based with a meaningfully higher elite base (30 vs. 15). The user
also asked for elites to carry **better rewards** — Phase 4's acquisition
system doesn't exist to grant anything yet, so this became a `rewardTier`
(`'none' | 'standard' | 'better'`) stub on `EncounterOutcome`, reusing
`DESIGN.md`'s own existing reward-scoping language, same "stub now, wired
in later" treatment as Merge. Tuning the elite enemy loadout needed an
actual empirical sweep, not guessing — Breach/Containment turned out to
be a sharp positive-feedback race where even `amount: 6` vs. the player's
`5` crushed the player to a ~2% win rate; `5.3` landed a ~23% win rate
against ~60% for a regular fight. 143 tests.

**Checkpoint F** (`run.ts`): `playRun()`, the full orchestrator — layer
generation, free-roam traversal, Heat, real combat, tied together across
4 layers. `gatekeeperReachable()` exported so `noRouteRemains` could be
unit-tested directly against hand-built graphs rather than hoped for from
random seeds — which mattered: the first attempt at a `heatMaxed` test
(sweeping `exploreThenGatekeeper`, "visit everything") instead hit
`noRouteRemains` 96% of the time. Real finding, not a bug — visiting
every fight in a layer routinely closes more than the single node
checkpoint B's resilience guarantee promises safety against. Needed a
different scripted strategy (`wanderPreferringSafety`, greedily preferring
already-resolved/safe neighbors) to reliably reach `heatMaxed` instead.
154 tests, `npm run check` clean throughout.

**Refinement**: asked what refinement I'd recommend; proposed a sweep of
`playRun()` under fully default settings (real 4-layer scale,
`beelineToGatekeeper`) since everything tested so far used either toy
layers or a deliberately extreme strategy. 500 seeds found only a 3.8%
victory rate (63.6% quarantined, 32.6% no route remains, 0.75/4 layers
cleared on average) — not a Phase 3 defect: the representative test
loadout is static and never improves across a run, so surviving reduces
to four independent, un-upgraded coin-flips against each gatekeeper. At
the user's direction, folded this into `BACKLOG.md`'s Phase 5 section as
context for the eventual balance pass, with a note to re-run the same
sweep once Phase 4's acquisition system exists rather than tuning by feel
now.
