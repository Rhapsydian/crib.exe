## Key decisions

Explored the actual engine before proposing anything (`resolve.ts`,
`triggers.ts`, `combat.ts`, `subroutine-types.ts`, `mod-types.ts`/
`mods.ts`, `gauges.ts`, `run.ts`, `encounters.ts`, `shop.ts`,
`loadout.ts`, `merge.ts`, `heat.ts`, `map-types.ts`/`map-gen.ts`,
`traversal.ts`, `ai.ts` — three parallel Explore agents covering combat
internals, run/node orchestration, and the project's existing
strategy-injection pattern). Two real forks resolved live before
locking the spec:

1. **Reopen-closed-node semantics**: exploration surfaced that this is
   a genuine engine gap, not just content — `NodeState` only ever
   transitions `unresolved → inert`/`closed` today, no reverse path
   exists. Resolved: reopening sends the node back to `unresolved` (win
   the fight again), not straight to `inert` (no free pass) — matches
   the session-9 "recoverable, not automatic" framing and keeps a
   single-use item's power level in check.
2. **Content-validation-pass timing**: offered scoping straight to
   checkpoints (as literally asked) versus a quick content sample
   first, explicitly flagging the precedent-based risk either way
   (session 17 scoped before content existed and had to rescope; Mods'
   session 32 validation pass caught a real gap before implementation).
   User chose validation first — for both systems, not just Events (a
   follow-up ask after the first draft only covered Events).

Drafted and validated 8 concrete Events (spanning all 3 risk tiers,
every effect kind) and 8 concrete Burners (spanning both new
`MapBurnerEffect`/`ShopBurnerEffect` unions, plus two archetypes' worth
of reused combat `PayloadEffect` kinds) against the proposed type
system. The Event sample surfaced a real gap — a reward grant can't
hardcode a specific piece id as the pool grows, so `EventEffect`'s grant
fields needed a `Grant<T> = {specific} | {randomFromRarity}` shape,
built into the type design directly rather than left as a known issue.
The Burner sample found no gap — confirmed the type system rather than
just filling it out, mirroring how Mods' session 32 also confirmed a
near-miss wasn't a real gap.

Two other findings, stated rather than asked (precedent already pointed
one way): combat-context Burner effects reuse the existing
`PayloadEffect` catalog directly via `resolvePayloadCore` (confirms
what session 36's write-up flagged as unconfirmed); every existing
"player decision" in the engine is a separate loosely-typed optional
strategy field, never a bundled `strategies: {...}` wrapper, so new
Burner/Event strategy types follow that same convention rather than
introducing a new pattern.
