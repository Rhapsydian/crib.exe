# Session 7 — 2026-08-23

`/decision-session`, resolving "how new subroutines are acquired during
a run, and whether there's a loadout size/slot limit" — flagged as an
open question since session 1.

Most of this landed in one round, mostly proposals confirmed as-is:
**combat rewards** (choice after a fight, StS-style) + a **shop** (spend
a new currency, **Data** — stolen data sold on a black market — on a
specific pick) as the two designed channels, events flagged as a probable
third but not designed (events themselves don't exist yet); reward
quality scaling with encounter difficulty (regular vs. elite/gatekeeper);
reward pool scoped to the player's class's 2 specialized archetypes plus
a smaller universal pool — a nice callback to session 4's Chained/
Always-Cantrip already being archetype-agnostic.

The one real fork was loadout structure: unlimited, or a slot cap? Landed
on a **capped installed loadout separate from an owned bench** — since
subroutines are always-evaluated every turn (no draw step like StS),
unlimited would risk late-run unreadability, so a cap isn't just a
balance knob, it's structurally necessary. Acquiring more than you can
slot isn't wasted, it's optionality for swapping between fights. Exact
slot number explicitly left to playtesting (6, echoing Cribbage's dealt
hand, floated as a thematic idea, not a commitment).

User added one thing after confirming: the slot cap itself can grow via
meta-progression, joining `DESIGN.md`'s existing persistent-unlock list
(new subroutines, classes, Ascension difficulty, expanding passive pool).

Before committing, the user raised a directly-related follow-on: how
does acquiring a *duplicate* of an already-owned subroutine work? Folded
into this session rather than opening a new one, since it's tightly
coupled to the acquisition flow just designed. Landed on: a duplicate
becomes held **material** on the bench (not an auto-merge, not a second
slot-hungry copy — a straight duplicate would be a strictly worse reward
than a new subroutine given the capped loadout); a new **Merge** map
node type (a deliberate git/version-control pun, fitting the setting
precisely) is where material gets spent to upgrade the base copy; merging
improves magnitude/efficiency only (bigger payload, lower threshold,
higher Scaling bank cap), never payload sub-type or trigger family, since
those are core identity. Likely rank-capped, exact number TBD like the
loadout slot count.

Updated `DESIGN.md` with a new "Subroutine acquisition" subsection under
Meta-Progression (including the duplicate/Merge-node paragraph), a Merge
node mention in Map & Run Structure, plus the slot-cap-growth bullet
added to the existing meta-progression list; `BACKLOG.md`'s Phase 0 item
marked done. Still docs-only, no code.
