## Key decisions

Paced one checkpoint at a time (verify, report, wait for explicit
go-ahead), not all ten in one sitting the way session 34 did Mods' nine
— confirmed with the user up front via `AskUserQuestion` before
starting. Two Explore agents verified the session-37 spec's exact
file/function claims against current code before planning (a discipline
session 34 itself established); most of it held, but a few real
corrections surfaced and were folded into the plan before writing any
code:

- `resolvePayloadCore` isn't exported -- the real entry point everything
  else in the engine uses is `resolvePayload`, which also layers in
  Primed/onFire passive hooks. Burners' combat effect goes through that,
  not a narrower hook-free path.
- No `step()` function exists to hook into for combat-context activation
  -- `step` is a generic closure used ~10 times for state-commit/peak-
  tracking. The real insertion point is `combat.ts`'s per-occurrence
  turn loop, indexed by side rather than needing a special enemy-side
  guard (the enemy's strategy just defaults to never-activate).
- `TraversalStrategy` lives in `run.ts`, not `traversal.ts` (a pure
  graph-mechanics module with no strategy types at all) -- the new
  `MapBurnerStrategy` followed the real precedent, not the file the spec
  named.
- `acquireMod` lives in `run.ts`, not `mods.ts` -- `acquireBurner`
  mirrors its real location.

Checkpoint E surfaced a real naming collision risk in the plan itself,
caught before writing code: the plan's own paraphrase had accidentally
reused "BurnerShopStrategy" for both checkpoint E (spend a carried
coupon) and checkpoint F (buy from the Burner Shop slate). Corrected to
the original session-37 naming (`ShopBurnerStrategy` for E,
`BurnerShopStrategy` for F) before either was implemented, so there was
never an actual collision in the shipped code.

Checkpoint D needed one real design call beyond what the spec described:
`reopenNode` was extracted into its own exported, hand-graph-testable
helper (mirroring `gatekeeperReachable`'s own Phase 3 precedent), since
checkpoint J's own stated intent ("a hand-built graph with a closed
node, same style `gatekeeperReachable()` got") only makes sense if the
transition itself is a real, isolated function rather than inlined in
the traversal loop.

Content authoring for Burners' combat-effect magnitudes and Events'
concrete numbers (session 37 explicitly left these TBD/playtesting):
Flash Drive/EMP Charge reused `subroutines.ts`'s own COMMON/UNCOMMON
burst tiers directly (5/8) rather than inventing new numbers, and the 8
Events were authored fresh this session (no numbers existed yet from
session 37, only names/kinds) using existing magnitude conventions and
real subroutine/Mod/Burner ids for specific grants (`pool()`,
`MOD_DEFINITIONS`, `BURNER_DEFINITIONS`) rather than placeholder
strings.

Checkpoint J's own verification found two real gaps from earlier
checkpoints, both fixed in the same pass rather than filed away:

- `eventChoiceStrategy` was threaded through `resolveEncounter` at
  checkpoint H but never added to `RunOptions`/`playRun` -- a script
  driving a full run had no way to influence Event choices at all.
  Caught while building checkpoint I's own end-to-end verification.
- `resolveFight` never actually passed `burnerActivationStrategies` to
  `playCombat` -- checkpoint C's whole combat-context mechanism was
  unreachable from a real run, only from a direct `playCombat` call
  (like the checkpoint's own manual smoke test happened to do). Caught
  while writing `burners.test.ts`'s smoke test.
- A third, more structural gap surfaced directly by `burners.test.ts`:
  the `noRouteRemains` reachability check ran *before* the map-Burner-
  activation step each loop iteration, so Skeleton Key's reopen effect
  could never fire in its own primary use case -- the run already ended
  the instant a closing node cut off the last route, before the player
  ever got a chance to spend the one Burner designed to save exactly
  that situation. Reordered the check to run after activation; verified
  with a real before/after (the same empty-loadout/`exploreThenGatekeeper`
  scenario ends in `noRouteRemains` without Skeleton Key, and carrying
  it genuinely changes that outcome).

**Balance pass** (user-initiated, after a fresh 6-class/200-seed/
beeline+explore sweep -- the first with real Event/Burner content live,
so not directly comparable to sessions 34/35's baselines):

- **Blackhat's explore-mode Heat fragility** (2.0% win rate, 65.5%
  heat-outs) -- traced to the kit itself via an isolated single-fight
  test (14.06 Heat generated from Blackhat's own kit alone vs. 0.00 for
  Warden/Operator), not movement Heat. Static Noise (an Always-triggered
  Cantrip, firing essentially every turn) was the dominant driver, more
  than Payload Drop's higher per-fire cost -- confirmed by isolating the
  two levers against each other empirically before picking a fix. Fixed:
  Static Noise `heatCost` 1→0, Payload Drop 4→3. Explore 2.0%→20.0%,
  beeline untouched (32.5%→33.0%), heat-outs 65.5%→34.5%. Deliberately
  didn't reach for full parity with beeline (a candidate that zeroed
  both costs hit 32.5% explore, erasing the gap) -- the user's own
  framing was that different ideal-playstyle floors per class are fine,
  a near-zero floor isn't.
- **Breacher's gatekeeper-tier fragility** (12.0% overall, worst of all
  6 classes) -- re-diagnosed from the session-28/29 "stalemate-prone"
  framing, which turned out not to be the actual driver anymore:
  Breacher wins ~90%+ against 5/6 regular enemies, and its gatekeeper
  losses are almost entirely real threshold losses, not attrition
  stalemates. A matched control sweep (same 6 gatekeepers, Operator/
  Warden as controls) found Firewall Prime plays the exact same
  mitigationBanked-accumulator strategy Breacher's own Lock Fatigue
  does, just far more efficiently (threshold 10 vs 28, payload 16 vs 5,
  2 banking sources vs 1) -- confirmed as a mirror-match power gap, not
  an archetype counter, since Warden (the only other Encryption-paired
  class) loses to it exactly as badly while Operator doesn't. Ghost
  Process and Incident Response are different mechanisms (Root
  gauge-denial with a self-accelerating Haste snowball; simply closing
  fights out too fast for Breacher's slow accumulator to matter).
  Tested 5 candidates against both the hardest matchups and easy
  controls before picking one: Buffer Overflow's trigger
  (`occurrence: run` → `occurrence: fifteen`) plus Lock Fatigue's
  threshold 28→20/amount 5→7. Beeline 12.0%→24.0%, explore
  12.0%→26.5%, no overshoot on easy matchups. Firewall Prime and
  Incident Response remain genuinely hard (0%/3% isolated) -- left
  alone deliberately, since both are broadly hard for other classes too.

## Notable problem-solving notes

- Checkpoint J's own verification work (writing real tests, not just
  reviewing the spec) found three real gaps across checkpoints C, D,
  and H -- none would have surfaced from code review alone, since each
  one only breaks when something actually calls the missing wiring end
  to end. Matches the project's standing "empirical, not guessing"
  discipline, just applied to implementation correctness rather than
  balance numbers this time.
- The Breacher re-diagnosis is a good example of not trusting a stale
  finding: session 28/29's "stalemate-prone, denial-only kit" framing
  was real *at the time*, but two sessions of engine changes since (the
  hard-tiebreak fix, Lock Fatigue's own session-29 retune) had already
  addressed the mechanism that framing was about -- rerunning the
  matched-control diagnostic before proposing a fix caught that the
  actual failure mode had moved to real threshold losses at gatekeeper
  tier specifically, a different problem than the one already on record.
- Both balance fixes went through the same discipline: isolate the
  mechanism with a targeted diagnostic (single-fight Heat generation;
  per-piece fire counts; matched-control sweeps against the same
  enemies) before touching any numbers, then test multiple candidates
  against both the failing matchups *and* easy controls to catch
  overshoot -- session 29 had already overshot once tuning this exact
  Lock Fatigue piece, so re-checking easy-matchup win rate at every
  candidate wasn't optional.
