## Goal

Plan and run a balance pass from `BACKLOG.md`'s "Balance — the active
arc": the `GAUGE_THRESHOLD` archetype-preference hypothesis, the 35.3pp
class dispersion, and the non-monotonic per-layer difficulty curve.

## The user's idea, which redirected the session

Proposed during planning, before any decision was settled: a utility
gatekeeper usable at any layer with a **specified pass rate**, resolved
by RNG rather than a real fight — so gatekeeper difficulty stops
contaminating every other measurement, and real gatekeepers can be mixed
back in one at a time.

This turned out to be the right instrument for a problem that had not
been named yet. A lost gatekeeper fight returns `quarantined: true`
(`encounters.ts`) and ends the run outright, so **every layer's
population is strictly "whoever beat the previous layer"** — any
per-layer or per-class number was being measured on a cohort
pre-selected by exactly the trait being measured.

One correction the user made during design, which mattered: pass rates
are **per layer only, never per layer per class**. A per-class matrix
would bake class differences back into the instrument and defeat the
point of using it to measure them.

## Design decisions resolved live

1. **Scope: harness + diagnosis only.** Build and validate the synthetic,
   answer two questions, stop and re-plan. The 12-gatekeeper
   marginal-cost sweep stays behind the class audit in the roadmap's
   audit sequence.
2. **Null curve: designed monotonic, calibrated to band** — not flat, not
   `p=1`. Reads class spread in the regime the game would ship in, and
   produces a durable artifact: the first written-down per-layer
   difficulty target.
3. **The `GAUGE_THRESHOLD` sign test is in**, bounded to the sign.
   Insurance on the class-spread number, since Ghost's position in that
   spread might be an artefact of a constant chosen last session.
4. Held D1 at the end of checkpoint 4, when the findings argued for
   re-sequencing the roster work ahead of the class audit.

## Findings

### The gatekeeper roster is the balance problem

Holding the roster at a fixed per-layer curve collapses class spread from
**33.3pp to 11.0pp** and puts five of six classes inside the 10–20% band.
Only Ghost (−23.3pp), Breacher (+9.7) and Warden (+6.3) move; the other
three do not move at all.

The decomposition is clean because checkpoint 2 had already run the
control — a synthetic at today's *measured* rates keeps current
difficulty and removes only roster variance:

- real roster → measured-rate synthetic: 33.3 → 12.5pp (**variance**)
- measured-rate → designed monotonic: 12.5 → 11.0pp (**curve shape**)

Curve shape buys nothing. `BACKLOG.md` item 3 proposed fixing the curve
before per-class tuning; that is the cheap intervention and it is now
measurably close to worthless for dispersion.

### The layer spike is layer 3, not layer 2

Unfiltered: **71.7 / 50.7 / 94.5 / 55.0**. Layers 2 and 4 are comparably
hard; layer 3 is a 44pp spike of easiness whose *entire* stable passes at
87.5–98.9% — while carrying the highest `magnitudeScaler` in the game.
**Payload magnitude is not what makes a gatekeeper hard**, which
invalidates the session 39 scaler as the roster's tuning lever.

Within-layer spread (57pp at layer 1, 45pp at layer 2) exceeds
between-layer spread (44pp). Which gatekeeper you draw matters more than
which layer you are on.

### `GAUGE_THRESHOLD` is roster-mediated

Ghost gains **+25.4pp** across 8→16 against the real roster and **+2.3pp
(ns)** against a flat one. The archetype-preference effect is real,
monotonic and large — but it is an archetype × *matchup* interaction, not
a property of the constant. Every flat-roster slope is ≤5pp, so **fixing
the roster makes the threshold usable as a difficulty lever again**.

Also: the threshold is a dispersion dial. Spread runs 16.4 → 33.3 →
42.0pp across 8/12/16, so session 48's 8→12 change cost ~17pp of
dispersion by itself — knowingly bought for content design space above
the floor of 4, but never before priced.

## Problem-solving notes

**The central prediction was wrong, instructively.** Layer 3 was expected
to collapse once de-confounded, since its cohort is normally pre-selected
by layer 2's 55% filter. It moved **0.1pp** on a 4× larger sample.
Selection appeared at layer 4 instead (−11.9pp). The generalisation worth
keeping: **survivorship bias only manifests where outcomes are sensitive
to cohort strength**, so the layers most in need of de-confounding are
the ones that already look balanced.

**A second wrong lean, corrected by measurement.** Going into checkpoint
5, the guess was that session 48's Ghost inversion had been noise at 150
seeds. It is real, reproducible, and *larger* than session 48 measured.

**Session 48's before/after table is not a threshold experiment.** Its
"before" column is the pre-session-48 engine, so it confounds
`GAUGE_THRESHOLD` with four other checkpoint changes shipped alongside
it. This session's sweep varies the threshold alone, on one engine.

**A validation criterion had to be corrected before it could be used.**
The plan's gate was "reproduce the funnel and per-class win rates within
SE." That is unachievable even by a perfectly faithful harness: the
synthetic makes each gatekeeper an independent coin, destroying the
correlation between a run's strength and its outcomes. The gate became
layer 1 as a **control** — pre-selection has not occurred there in either
regime, so any divergence is a real bug. It came back identical to the
digit (2310/2310 reached, 3.75% attrition, mean cohort power 10.133).

**Aggregating classes over shared seeds does not multiply the sample.**
Chased after a 3.7pp discrepancy between a 200-seed and a 400-seed
measurement of the same quantity. The first hypothesis — mulberry32
correlating across sequential low seeds — tested clean (varRatio
0.72–1.05×). The real cause: `createRng(seed)` builds the map before any
class-dependent divergence, so at one seed all six classes get the same
layout and the same gatekeeper — **400/400 seeds**. A six-class aggregate
carries **3.47×** the variance of an independent sample; true SE is ~1.9×
the naive figure. Now in `README.md`'s conventions. Per-class numbers are
unaffected.

**The trace constant deleted a distribution.** Real gatekeeper trace is
skewed (mean ~2.8, median 0), and feeding the mean dropped `heatMaxed`
12.5% → 10.5%. `traceGenerated` now accepts `number | number[]`, sampled
via a hash of the same seed the coin reads, so a distribution still costs
exactly the one RNG draw a real fight costs. Recovers to 11.3%; the
residual is inherent, since real trace correlates with run state and the
synthetic cannot.

**Behaviour-neutrality was proven, not argued.** An md5 fingerprint over
`playRun`'s full log, outcome, final Heat and loadout across 100 seeds ×
6 classes came back byte-identical before and after checkpoint 1
(`5ba7a781b159c42b7a24faadfbd06e0b`). The two directional tests were
mutation-checked — forcing the coin to always pass fails both — and the
`passRate: 0` test carries an explicit non-vacuity counter, the shape
session 48's instrument audit found in `burners.test.ts`.
